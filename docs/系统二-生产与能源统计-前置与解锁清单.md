## 2. 四条硬依赖（表结构证据）

以下不是「数据还没录」，而是**表结构决定了这些数只能由别人写出来**：

1. **`p2_output_record` 没有 `order_id`。** 订单归属只存在于 `p2_finished_allocation`（`order_id`、`reservation_id NOT NULL`）。没有称重归属（R12），E03 的订单权重就没有分子。
2. **`p2_finished_allocation.reservation_id NOT NULL`，FK 到 `p2_stock_reservation`。** 预留行只能由统一库存服务在建行事务里生成——这就是为什么先有库存服务才有归属。
3. **`p2_stock_cost_ledger.cost_run_id NOT NULL`，FK 到 `p2_cost_run`。** 成本流水只能由核算运行产生。**因此 K01（库存成本视图）、K02（成本流水）依赖 K05（补算引擎），而不是反过来**——排期时不要先做 K01/K02。
4. **`p2_energy_allocation.cost_run_id NOT NULL`。** 分摊结果落库同样挂核算运行；E03 现在是查询时计算，落账要等 K05。
5. **库里没有任何「日确认」表。** R19（当日录全确认）需要持久化日状态（车间 × 日期 × version × sourceRevision），当前无表可写。这是一次 **DDL**，需要走迁移评审（V15+，Flyway 默认关闭）。

## 4. 一期能源采集（外部卡点）

`dws_energy_day`、`dws_energy_hour`、`dim_energy_type`、`dim_energy_tariff` 至今 0 行，`dim_sensor` 10 个测点 0 个绑定 `energy_type_id`。E01/E02/E03 的代码已按「缺测不填零」完成，采集一通即自动出数，**无需改代码**。需要计量班组做两件事：绑表（`energy_type_id`、范围与父子关系）、核验覆盖（之后打开 `phase2.energy.coverage-verified` 开关，接口才会给出 `COMPLETE`）。

## 5. 建议的推进顺序

1. **本模块（我们）**：已完成 E01—E06。剩余工作只剩等数据与等前置，**没有可独立推进的代码项**。
2. **需要组内决策的一件事**：R19 的日确认表 DDL（影响 E03 完全体与 R18 的口径），建议先出设计再评审。
3. **需要排期对齐的两件事**：统一库存服务（K05 的前置）、一期采集启动（E 系列出数的开关）。
4. **K 系列明确挂起**，直到统一库存服务与生产事实写入落地；先做只会产出假均价与假盈亏。
