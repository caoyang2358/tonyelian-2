## 1. 先分清是哪一种交付

三种交付形态对数据的处置完全不同，混着做会留后患：

| 交付形态 | 数据处置 | 判断标准 |
| --- | --- | --- |
| **演示交付**（只展示功能，不接真数据） | 可保留 `DEMO-SEED`，但页面必须有「含演示数据」标识 | 看的人知道这是演示，就不构成误导 |
| **试运行交付**（客户开始录真实数据） | **必须清空全部模拟读数与虚构单据**，只保留一期主数据 | 真假混在一起后再也分不清哪条能删 |
| **生产交付**（验收上线） | 清空模拟数据 + 接通真实采集 + 移交本文件第 4 节责任清单 | 数据责任要落到具体部门 |

**硬规则：演示数据可以进演示环境，绝不能进生产环境。**

## 6. 已知局限（主动说明，别等被问）

1. **无法一键清除全部演示数据**：只有测点和读数两张表带来源标记（`data_source` / `source_system`）。设备、参数、单位、供应商、合同、附件、提醒设置均无标记，只能按编码规则（`EQUIP-DEMO-`、`HT-2026-001`）或人工识别。彻底解决需给这些表增加来源列，属于 DDL 变更，本轮不做。
2. **一期源码不在本仓库**：设备与测点编码只能追溯到一期 V2 元数据的摘录注释，没有原文件副本与校验值；结构快照有 SHA-256，数据没有。要核对全量与一致性，需一期只读库或重新取得一期源码。
3. **快照版本口径**：结构快照取自 `bea8047f…`，文档指定基线为 `b8f1231c…`，差异未比对。

## 8. 真实数据到手后的替换手册

> 第 2 节回答「交付前清什么」，本节回答「清完怎么把真数据接进来」。这是评审意见第 5 条的后半段，也是最容易被漏的一环——**替换不是删掉假数据就完了，而是要让真数据在三条链路上同时生效**。

### 8.1 要替换的是四类东西，处理方式各不相同

| 类别 | 当前实例 | 假在哪 | 替换方式 |
| --- | --- | --- | --- |
| **脚本读数**（B 类） | `TEMP-001` 20 条，`source_system='DEMO-SEED'` | 公式生成，非实测 | 删除 → 由采集器写入 |
| **虚构单据**（C 类） | 供应商、合同、附件（已于 2026-11-12 清理为 0） | 编造的客户与合同号 | 已清空，等真实录入，**不需要替换动作** |
| **占位值** | 8 台责任人 = 「待指定」 | 不知道真实责任人，用可识别占位代替 | 拿到名单后按值批量替换 |
| **推定值** | 8 台管理状态 = 「在用」 | 按编码与工艺推断，未经现场确认 | 现场核实后逐台更正，**必须走接口**（见 8.3 第 4 步） |

主数据（8 台设备编码、10 个测点编码、车间、单位）**不是假数据**，是一期真实资产，替换过程中一行都不能动。

### 8.2 三条硬约束决定操作顺序（顺序反了会出问题）

| 约束 | 依据 | 后果 |
| --- | --- | --- |
| `ads_parameter_monitor` **没有来源列** | 表结构只有 `sensor_id/parameter_id/...`，无 `source_system` | 快照只能按测点整行删，**先接真数据再清理 = 把真实快照删掉** |
| 有读数记录的测点**编码冻结** | S1-P05：有采集记录时删除返回 409 | 若现场核对发现编码要改，必须**在数据入库前**改，否则改不动 |
| `uk_ods_sensor_source_record` 唯一 | `(source_system, source_record_id)` | 采集器重发同一条消息会被拒，`source_record_id` 必须由采集方提供且稳定 |

**所以顺序只能是：备份 → 清演示 → 接采集 → 核验 → 补占位值。** 不能边接边清。

### 8.3 分步执行

**第 0 步：备份读数两张表**（演示数据可重放，真实数据不可）

```bash
mysqldump --single-transaction --no-create-info -h127.0.0.1 -P3308 -u<用户> -p \
  copper_phase2_dev ods_sensor_data ads_parameter_monitor > .local/backup/readings-before-real.sql
```

**第 1 步：清除演示读数**（全库口径，不用脚本默认参数）

```sql
-- 1.1 先看清范围：当前应为 DEMO-SEED 20 条 / 1 个测点
SELECT source_system, COUNT(*) 条数, COUNT(DISTINCT sensor_code) 测点数
  FROM ods_sensor_data GROUP BY source_system;

-- 1.2 物理删除演示读数（is_deleted 是业务软删标记，演示数据直接物理删）
DELETE FROM ods_sensor_data WHERE source_system = 'DEMO-SEED';

-- 1.3 清掉「已无任何有效读数」的快照行
--     接真数据后 ods 里有记录，这些行不会被命中，所以这条是幂等安全的
DELETE m FROM ads_parameter_monitor m
 WHERE NOT EXISTS (
        SELECT 1 FROM ods_sensor_data d
          JOIN dim_sensor s ON s.sensor_code = d.sensor_code
          JOIN dim_sensor_parameter p ON p.sensor_id = s.sensor_id
         WHERE s.sensor_id = m.sensor_id
           AND p.parameter_id = m.parameter_id
           AND p.parameter_code = d.parameter_code
           AND d.is_deleted = 0);
```

**第 2 步：接通真实采集**

二期**没有采集写入接口**——后端只有 `P09`（读 `ads_parameter_monitor`）和 `P10`（读 `ods_sensor_data`），全部只读。真实数据由外部链路写入，需要采集方确认三件事：

| 写入点 | 要求 |
| --- | --- |
| `ods_sensor_data` | 按 `sensor_code + parameter_code + collect_time` 写入；`source_system` 填采集系统标识（如 `PHASE1_COLLECTOR`）；`source_record_id` 填消息 ID |
| `ads_parameter_monitor` | **必须同步维护**。该表由「既有采集/聚合链路负责写」（见《数据库逻辑表设计与成员使用指南》），只写 ods 不写快照，则页面最新值永远显示「待数据」 |
| 单位 | `source_unit` 与 `dim_unit` 对齐，否则页面单位与数值不匹配 |

**第 3 步：核验五项**

```sql
-- 3.1 来源分布：应只剩真实来源，无 DEMO-SEED
SELECT source_system, COUNT(*) 条数, MIN(collect_time) 最早, MAX(collect_time) 最新
  FROM ods_sensor_data WHERE is_deleted = 0 GROUP BY source_system;

-- 3.2 覆盖度：哪些测点还没有数据（10 个测点中应为 0 条未覆盖）
SELECT s.sensor_code, COUNT(d.record_id) 条数
  FROM dim_sensor s LEFT JOIN ods_sensor_data d
    ON d.sensor_code = s.sensor_code AND d.is_deleted = 0
 GROUP BY s.sensor_code HAVING 条数 = 0;

-- 3.3 快照一致性：快照最新值应等于原始表最新一条
SELECT m.sensor_id, m.latest_value 快照值, m.latest_collect_time 快照时间,
       (SELECT d.value_num FROM ods_sensor_data d
          JOIN dim_sensor s ON s.sensor_code = d.sensor_code
         WHERE s.sensor_id = m.sensor_id AND d.is_deleted = 0
         ORDER BY d.collect_time DESC LIMIT 1) 原始表最新值
  FROM ads_parameter_monitor m;
```

人工确认另两项：`quality_code` 取值在 `GOOD/BAD/UNCERTAIN` 内；页面「数据过期」提示消失（它按 `latest_collect_time` 判断，数据一进来就自动恢复）。

**第 4 步：补占位值与推定值**

| 对象 | 做法 | 为什么不能直接 UPDATE |
| --- | --- | --- |
| 8 台责任人 | 界面逐台改，或脚本改的同时补 `p2_change_log` | 直接 UPDATE 不留变更记录，日后问「这名字谁改的」无法回答 |
| 8 台管理状态 | **必须走 `PUT /api/v1/equipment/{id}`**（带 `expectedVersion`） | 该接口写版本号与变更原因，是「状态何时由谁改」的唯一证据 |

**第 5 步：收尾**

- 确认提醒设置提前量（现为质保 15 / 维保 45，仍是演示值）
- 更新《数据来源说明.md》第 2 节的行数与来源列
- 第 4 节责任清单请各方签字，替换完成时间写入本文件

### 8.4 前端和接口不用改

这是当初设计的直接收益，可以明确对外讲：

| 位置 | 行为 | 是否需要改 |
| --- | --- | --- |
| 读数弹窗来源列 | `DEMO-SEED` 时显示「演示数据（脚本生成）」，其他值原样显示 | ❌ 真数据进来后自动变成采集系统名 |
| 设备页标题 | 演示标识已于 2026-11-12 移除 | ❌ |
| `P09` / `P10` | 只按 `sensor_code + parameter_code` 查询，不认来源 | ❌ |
| 数据过期判断 | 按 `latest_collect_time` 计算 | ❌ 自动恢复 |

### 8.5 回滚边界

- 清掉演示读数**可以重放**：`python scripts/seed_demo_readings.py` 会按固定随机种子重新生成同样的 20 条。
- 真实采集接入后**不要再跑** `seed_demo_readings.py --clean`：它按 `sensor_id + parameter_id` 删快照，不区分来源。
- 测点编码一旦有读数记录即冻结。若现场核对发现编码与铭牌不一致，必须在第 1 步之前完成更正，否则只能停用后重建。
