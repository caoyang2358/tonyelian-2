## 2. 请求、响应与类型

| 项目 | 约定 |
| --- | --- |
| 路径 | 统一 `/api/v1`；模块清单表中省略此前缀 |
| 数据来源 | 前端只调用二期后端；二期通过MySQL读取一期数据，不调用一期API |
| 常规请求 | JSON，`Content-Type: application/json`，UTF-8；文件上传使用multipart |
| 成功响应 | 延续HTTP 200及现有信封，不因新增业务另建一套成功格式 |
| 字段名称 | JSON使用camelCase；数据库字段名不直接成为对外接口约束 |
| 新增接口中的ID | 十进制字符串，例如`"12"`，不让浏览器用浮点数处理BIGINT |
| 现有ID兼容 | 当前S1-E01的`id/workshopId`是JSON整数，前端已经转字符串。首批保留兼容；后续统一成字符串时需同批更新DTO、测试和文档，不静默改变其他字段结构 |
| 生产重量 | 吨，十进制字符串，最多3位小数，返回规范化3位，例如`"1.250"`；超精度拒绝，不静默取整实际称重 |
| 金额 | 人民币元，十进制字符串，最多2位小数；返回例如`"1200.00"` |
| 单价/均价/分摊比例 | 十进制字符串，保留计算精度；不能先把均价截成两位再乘重量 |
| 其他数量 | 页码、计数、版本及整数使用年限等仍是JSON整数；布尔值为true/false |
| 日期/时间 | 业务日`YYYY-MM-DD`；时刻使用带偏移的ISO 8601，例如`2026-11-02T08:30:00+08:00`；统一Asia/Shanghai |
| 可空值 | 缺失资料返回null及相应缺项/状态；真实已知零返回0或`"0.000"`，不能相互替换 |
| 字符串 | 去掉姓名、编码等两端空白；保留说明正文实际内容；必填不能以空串代替 |
| 凭据/物理路径 | 响应不返回数据库密码、连接配置、服务器文件绝对路径或异常堆栈 |

设备技术参数、原始传感器值和能源读数不统一按“重量三位小数”裁剪，应遵循其单位和已配置精度。`sensorCode + parameterCode`是采集值匹配依据，不能用页面中文名代替。

现有信封继续使用：

```json
{
  "code": "OK",
  "message": "成功",
  "data": {},
  "timestamp": "2026-11-02T08:30:00+08:00"
}
```

新增分页列表约定如下，`page`从1开始，`pageSize`默认20、最大100；具体排序及过滤项见模块清单。S1-E01现有`data.items`保持可用，新增分页字段是后续扩展。

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

## 3. 写入、并发和重复请求

| 字段/机制 | 使用规则 |
| --- | --- |
| `requestId` | 所有有副作用的JSON命令必填；前端为一次用户提交生成UUID，超时重试沿用同一个值 |
| `operatorName` | 写入时手填经办人；不是登录用户，也不是已认证身份 |
| `expectedVersion` | 修改/更正/删除/推进已有对象时传入查询到的整数版本；创建新对象不用传 |
| `reason` | 重要更正、取消、减量、人工不足结束、超差放行和误建删除等场景必填；普通首次录入无需另加审批理由 |
| `version` | 新业务对象返回当前版本；现有共享主表没有该字段，不通过读请求偷偷补写表数据 |
| 幂等 | 同一操作、目标及requestId、相同业务内容重复提交，返回第一次已成功的业务结果，不再次入库、扣库、预留、交付或报修 |
| 请求ID冲突 | 同一requestId改成不同业务内容，返回409；修改草稿后重新提交应生成新requestId |
| 处理顺序 | 先查已成功幂等结果，再进行版本判断；否则第一次成功后的正常重试会因版本已变而误报冲突 |
| 持久化范围 | 请求标识及结果关联存入数据库，不能只靠按钮禁用或内存集合；不强制新建一项对用户可见业务模块 |
| 事务与锁 | 后端以数据库事务和必要锁/版本校验处理；前端传来的库存余额、均价和利润不能直接作为最终写入值 |

多对象保存时，除根对象版本外，接口还应携带所依据的订单/计划版本或快照标识；服务端必须重新核对当前库存与产能。具体锁实现属于研发选择，不让用户选择回滚算法。

允许创建的单例/日期设置PUT可明确使用`expectedVersion:null`表示“预期该设置尚不存在”；发现已存在时409，不能借null跳过已有版本校验。共享主数据版本覆盖经二期受控入口的写入，接入现用库前仍须协调同字段的其他写入方，不能用二期版本宣称已保护任意外部改表。

DELETE采用统一JSON客户端发送确认体，包含`requestId/expectedVersion/operatorName/reason/confirmed`；前端与Vite转发需联调验证该请求体，不把理由塞进日志易暴露的长URL。二次确认只用于基线明确要求的误建删除等操作，不扩大到排产的两次人工确认。

## 4. 错误和业务结果

错误也沿用信封。共享 BusinessException 的字段错误为 data.fields 对象；运维 InvalidRequestException 使用 data.fieldErrors 数组。共享前端 requestApi 兼容两种结构；知识库复用该客户端。data 还可按需要返回 conflicts/missingItems，不得原样返回数据库异常文本。

```json
{
  "code": "VERSION_CONFLICT",
  "message": "该设备已被更新，请刷新后重试。",
  "data": {
    "currentVersion": 3,
    "conflicts": [{"objectType": "EQUIPMENT", "objectId": "1"}]
  },
  "timestamp": "2026-11-02T08:30:00+08:00"
}
```

| HTTP | code | 场景 | 实现状态 |
| --- | --- | --- | --- |
| 200 | `OK` | 正常响应；列表无记录也是成功 | 已有 |
| 503 | `DATABASE_UNAVAILABLE` | 数据库不可用或所需结构无法查询 | 已有 |
| 404 | `NOT_FOUND` | 路径/对象不存在；后续补对象级检查 | 路径级已有 |
| 405 | `METHOD_NOT_ALLOWED` | 请求方法不支持 | 已有 |
| 500 | `INTERNAL_ERROR` | 未预期错误；只返回安全提示 | 已有 |
| 400 | `VALIDATION_ERROR` | 必填、格式、枚举或查询参数错误 | 待开发 |
| 400 | `PRECISION_EXCEEDED` | 实际重量/金额超出约定精度 | 待开发 |
| 409 | `DUPLICATE_CODE` | 设备/测点等唯一编码冲突 | 待开发 |
| 409 | `VERSION_CONFLICT` | 对象被别人更新 | 待开发 |
| 409 | `IDEMPOTENCY_CONFLICT` | 相同requestId携带不同业务内容 | 待开发 |
| 409 | `RELATED_DATA_EXISTS` | 有业务关联，不能硬删除 | 待开发 |
| 409 | `INSUFFICIENT_STOCK` / `CAPACITY_CONFLICT` / `SUPPLY_CONFLICT` | 确认或实际保存时库存、产能、供料条件发生冲突 | 待开发 |
| 409 | `STATE_CONFLICT` | 当前状态不允许该操作，例如覆盖已有实际 | 待开发 |
| 422 | `MISSING_REQUIRED_DATA` / `HANDOVER_REASON_REQUIRED` | 该操作缺少必要依据，或超5%却没有放行原因 | 待开发 |

以下是正常业务结果，不能都当作接口调用失败：

- 可行性评估发现需调整：HTTP 200，返回缺料/未排量/延期原因和可编辑草稿；不再次启动一轮业务评估。
- 产量或能源尚未登记：查询返回待统计及null，不能伪装成已知零。
- 实际称重已保存但成本不齐：数量保存成功，核算状态待核算，返回缺项；不能因材料金额或能源暂缺就丢掉已确认的真实数量。
- 一项成本只算出部分：已知金额、缺项和完整性一起返回；不得以部分成本算出一个看似完整的利润。
- 取消订单：保留实际及成本，不返回“负的原合同利润”。

## 5. 必须一起成功的操作

| 对外命令 | 一个后端事务必须覆盖 |
| --- | --- |
| 设备新增/编辑 | 共享主数据允许字段、二期档案扩展、版本、重要更正记录 |
| 一次确认排产方案 | 当前条件校验、有效计划/任务、原版本替换、相应库存预留及预期供料承诺 |
| 铜板实际领用/投入 | 实际数量与金额依据、实物扣减、对应预留核销、库存流水 |
| 铜杆称重 | 新增合格产出、一次入库、可确定成本来源/待核算状态；多订单关联不能再入一遍 |
| 铜杆领用交接 | 交出/接收事实、按交出量一次扣库与核销预留、上游成本依据；不能接收确认再扣一次 |
| 铜丝称重 | 同规格实际新增总量、订单归属、公共差额、成品入库与预留、成本归属依据 |
| 公共成品分配 | 分配数量、对应预留、公共自由份额及成本转归；不扣实物总量 |
| 实际交付 | 交付事实、成品实物及预留核销、相应库存成本转出 |
| 重要更正 | 原记录留存、修正记录、库存差量/成本修正关联、版本及留痕；失败整体回滚 |

成本资料缺失时保存“已知/待核算”依据，不要求在一笔数量事务里伪造全部成本。补算读取事实生成受控核算版本，不重复执行原数量流水。

库存只经过统一后端StockService/CostService。**不对页面开放“直接设置余额”“任意增加预留”“保存计划后再调一次预留”的接口。**外部接口由业务动作组织，内部服务不需要都变成HTTP接口。

## 6. 计划、状态和统计的特别约定

- 查询和评估没有业务写入副作用。排产草稿优先保留在当前页面；关闭未保存不发任何正式预留/撤销命令。浏览器内草稿标识不是正式planId。
- 系统建议与人工调整共用同一草稿结构，只有一个确认命令。确认时自动校验不是第二次人工审批；冲突返回原草稿修改。
- 未来未开始任务可以一起重排；已有投入、领用、称重的部分冻结，不能重排覆盖。
- 物料供料必须按日期及同日先后表达。未来计划铜杆不作为实物；铜板计划需求按净新增铜杆合并后乘1.05、向上取到0.001吨一次。
- 生产结果、交付情况、核算完整性分别返回；任务执行记录与订单最终生产结果也分开。
- 日产量/订单已生产量来自称重事实。库存分配、铜杆产出和预留不重复计为铜丝新生产量。
- 能源返回电/水/煤气各自数量、单位、覆盖/质量与缺项，不能跨单位求一个“总能源数”；小时、日表同一范围不能重复相加。
- 组网位置不改变设备真实归属；参数恢复不结束维修；报警不自动报修；任何“开始/停止/结束”接口均只记录人工确认的事实，不控制现场设备。
