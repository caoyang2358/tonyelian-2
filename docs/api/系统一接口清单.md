# 系统一接口清单（研发设计草案）

日期：2026-11-02。范围：设备管理、运维管理、运维知识库、设备组网四个主入口。

业务依据为[需求基线第12—14节](../需求基线.md)及[数据库逻辑表设计](../数据库逻辑表设计与成员使用指南.md)。原型只用于核对页面入口和操作，不覆盖已确认业务。本文是接口拆分建议，**只设计、不实现**；物理表与字段仍须在对应开发批次形成迁移和详细契约。

**当前仅 `GET /api/v1/equipment` 已实现最小只读查询。本文其余接口均待开发。**已有设备查询当前返回 `data.items`，没有分页、名称筛选、类型筛选、设备扩展档案、测点或维修关联；不能把清单中的扩展列当成现成功能。

公共类型、错误和幂等顺序沿用[接口通用约定](接口通用约定.md)。设备首批接口 S1-E01—E06 的完整字段、示例和兼容策略以[首批接口约定](首批接口约定.md)为准。共享 `GET /api/v1/reference-data` 由首批约定统一提供车间、工序、单位、类型及状态选项；本文不另建工序、单位字典 CRUD。

## 1. 全部接口共用约定

| 项目 | 本清单约定 |
| --- | --- |
| 路径 | 表中省略统一前缀 `/api/v1`，例如 `/equipment` 实际是 `/api/v1/equipment`；不调用一期 HTTP 接口，通过二期后端的数据访问层复用约定的一期表 |
| 响应 | 沿用工程响应外壳；下表“出参”指 `data` 内字段。错误响应不泄露 SQL、连接信息或文件真实存储路径 |
| 新增集合查询 | 分页返回 `data.items / page / pageSize / total`，页码从1开始；支持的筛选和排序字段须白名单化。详情内有限的参数快照、布局元素和引用集合不是额外分页接口 |
| 已有设备查询兼容 | 现有 `data.items` 元素为 `id, code, name, workshopId, workshopName, responsiblePerson, enabled`；`id/workshopId` 当前是数字，其他新接口按字符串 ID 设计。首批升级须明确兼容，不能默默改变已有调用方 |
| 标识 | 新接口 ID 按十进制字符串传输；沿用已有设备、测点和参数身份，编码不能因改名、布局调整或内部编号生成而重编 |
| Decimal | 阈值、读数、技术参数中的十进制值和坐标以十进制字符串传输，可为负数，例如炉压阈值。整数秒、小数位、版本和分页计数仍用整数；缺失为 `null`，不使用0冒充缺失 |
| 日期 | 日期为 `YYYY-MM-DD`；时刻带时区偏移，例如 `2026-11-02T09:00:00+08:00`。业务时区 `Asia/Shanghai`；实际发生时间和录入/修改时间分开 |
| W：写请求 | JSON或multipart均包含 `requestId`、手填 `operatorName`。`requestId` 用于幂等：相同请求及内容只执行一次；相同标识不同内容返回冲突，不重复创建附件、工单或处理轮次 |
| U：已有对象更新 | 在W基础上带 `expectedVersion`；设备资料更正、规则修改、替换附件、巡检更正、布局保存及状态处理等带必要 `reason`。并发版本不符返回409并提示重新读取，不静默覆盖 |
| POST与版本 | 新建对象无已有版本；针对已有对象的POST动作，如报修提交/审核/维修/验收、事件人工处理，仍须携带该对象 `expectedVersion` |
| 审计 | 重要写入保存对象、前后值、理由、操作时间、手填人员及关联依据；返回 `version / updatedAt` 和必要 `changeLogId`。手填姓名不是登录身份或权限认证 |
| 写入边界 | `dim_equipment / dim_sensor / dim_sensor_parameter` 仅由统一主数据服务维护约定字段；二期扩展资料进入 `p2_*`。`ads_parameter_monitor / ods_sensor_data / dws_energy_*` 不由本清单接口写入 |
| 版本含义 | `version` 是业务对象并发版本；`ruleVersionId` 是不可改写的异常判断依据版本；二者不能混用。附件并发版本不等于建设文件历史版本系统 |

下表的 `W/U` 是上述公共字段的缩写，不表示可省略。DELETE的确认信息按首批契约发送，服务端仍在删除事务内重新检查关联；前端二次确认或先查到“可删除”不能替代该校验。

## 5. R16规则修改和事件边界的服务约束

1. P08保存配置时，校验参数对象版本；判断依据发生变化则生成不可覆盖的新规则版本，保存旧值、新值、时间、原因和人员。
2. 事务内只结束该参数受影响的活动事件，结束原因记 `RULE_CHANGED`；不填写假的自然恢复时间。无关测点/参数事件不被批量结束。
3. 后续从下一条有效采集数据应用新规则。普通参数重新累计配置的持续异常时间，关键参数按配置可立即提醒；不强加统一恢复等待秒数。
4. 同一测点、参数及规则版本的持续过程只生成一个事件；自然恢复记真实恢复时间，之后再满足条件才生成新事件。
5. 事件事实及原规则版本始终可追溯。A03仅记录人工处理，规则或事件变化均不修改维修状态；R05—R08是工单状态变化的业务入口。
6. 内部采样游标、防重、事件生成及恢复事务是研发实现责任，不向页面开放任意造事件、改读数或“强制恢复”接口。原型模拟按钮不直接转成正式业务写API。

## 8. 开发前需落实的技术点与明确边界

以下是研发落实事项，不是需要重新进行业务对齐的未决需求：

- 首批先固定E01已有DTO兼容、ID字符串转换、扩展表迁移、设备共享字段写入主责和全量关联删除检查，再开放新增/修改/删除按钮。
- 共享主数据的并发版本保存方式、附件存储位置/技术限制、JSON与关联表取舍、事件游标和去重、分页排序上限由团队设计，满足本文业务结果即可。
- 参数/规则配置写入、旧事件受控结束和规则版本记录须保持一致；若事件服务尚未开发，必须明确未完成能力，不能用一期 `limit_status` 冒充完整事件。
- 多对象更正、状态动作和附件引用更新需要原子保存及幂等；具体事务边界和失败清理由详细契约落实，不给用户增加技术审批。
- 预计寿命及提醒按资料计算，缺资料待补；在线/离线、管理状态、异常事件处理、维修工单状态各自独立。
- 不开放PLC地址/寄存器写入、设备开停机、任意采集值写入、自动报修、综合评级、自动巡检、短信邮件、Excel导入导出、完整采购/结算和文件历史版本功能。

业务覆盖对应基线12—14节、AC19—AC21及AC48；接口状态以本文件开头的实现说明和实际后端为准，不以接口数量或原型按钮数量计算开发完成率。
