# 订单、库存、排产与交付接口清单

日期：2026-11-02。状态：**接口设计建议，本文所列业务接口全部待开发**。工程初始化已经实现的健康检查、初始化概览、设备只读接口不计入本表；本文件不表示接口、业务表或对应页面已经实现。

业务依据以仓库内[需求基线](../需求基线.md)第3—7、9节为主，成本衔接遵守第11节；对象关系参考[数据库逻辑表设计与成员使用指南](../数据库逻辑表设计与成员使用指南.md)。历史原型`二期原型/v2/planning.js`仅用于核对已有页面和操作，不能沿用其中的`confirmSuggestion`、暂存预留、`finalize`及“冲突后放弃再评估”流程。

本文覆盖“订单与计划”主入口内的订单、物料库存、产能日历、方案与交付，不增加侧栏。具体URL、字段名和查询拆分是技术建议；后续调整需同步前后端、生产及成本调用方，不能改变已确认业务结果。

## 1. 所有接口的共同约定

| 项目 | 约定 |
| --- | --- |
| 根路径、响应 | 全部以`/api/v1`开头；沿用`{code,message,data,timestamp}`，成功`code="OK"`。以下“出参”均指`data`内字段 |
| ID与版本 | 所有业务ID以字符串传输，不写死某台开发库中的车间数值ID。`version`、`expectedVersion`、`expectedStockVersion`及范围版本为JSON非负整数，例如`0`、`1`，不能使用字符串版本；调用方传读取到的对应版本。多对象事务使用`expectedVersions`，每个对象的`version`同样为整数，不能只有页面本地版本。特殊日期PUT首次创建允许`expectedVersion:null`，仅表示预期该记录不存在；若已存在返回409，普通更新不得以null绕过版本检查 |
| 数量与金额 | Decimal字段用JSON字符串：`quantityTon:"1.001"`、`amountYuan:"100.00"`。重量吨最多3位、总金额人民币元最多2位；中间均价、单价不强行截成2位，不写死统一单价小数位。实际数值超精度报字段错误，不静默向上取整 |
| 缺失与零 | 未知数量、金额、日期返回`null`及必要`missingItems`；确认无货才是`"0.000"`，未知成本不是`"0.00"`。成本未齐不阻止合法数量事实保存；铜板不另建库存均价账 |
| 日期与时区 | 业务日期`YYYY-MM-DD`；时间用带`+08:00`的ISO 8601，统一`Asia/Shanghai`。业务发生日期与服务端`recordedAt`分别保存，不按补录当天归属历史事实 |
| 新分页 | 所有集合查询使用`page`、`pageSize`，统一返回`data.items/page/pageSize/total`；`page`从1开始。订单默认`dueDate ASC, createdAt ASC, id ASC`稳定排序，不因分页丢失交期顺序。日历查询也必须明确范围和是否完整，不能静默截断 |
| 人员、原因 | 所有业务写入携带手填`operatorName`；更正、优先级调整、取消、减量、改期、产能变更、分配调整必须有`reason`。人员不是登录账号，不新增审批权限 |
| 幂等 | 所有产生事实或改变业务状态的写入携带`requestId`。后端对操作类型与`requestId`建立唯一处理依据；同请求同内容重试返回原结果，不重复建单、预留、出入库或交付。同`requestId`不同内容返回409。不能只靠前端禁用按钮防重 |
| 更新与冲突 | 更新携带`expectedVersion`；计划、库存及成本跨对象变更在后端事务中完成。版本、库存、产能或供料冲突返回HTTP 409及安全说明，前端保留原草稿，不跳回业务评估；格式错误400、不存在404。失败不留下半套生效记录 |
| 错误数据 | 沿用根接口约定，`data`按需包含`fieldErrors`、`conflicts`、`missingItems`，仅返回适用项。冲突项应给对象ID、当前版本、差额/日期及受影响任务，不能暴露SQL、连接密码或异常栈 |
| 留痕 | 重要更正保留原值、新值、原因、人员、时间及库存/成本关联调整依据。历史事实不物理删除，不通过覆盖原计划抹去实际差额 |

`requestId`用于业务写入幂等；只读POST评估、影响预览可以携带请求跟踪标识，但**不建立库存预留、正式任务或产能占用**，不能把评估请求登记成已生效业务方案。

### 开发批次

- **P1 基础**：订单及物料定义、数量库存/期初/铜板到货、产能来源和查询。
- **P2 计划实际闭环**：人工编排同一草稿、一次确认保存、实际登记衔接、成品分配交付、订单更正及特殊结束结果展示。
- **P3 自动建议**：按已确认约束进行一次评估、联合试排和未来未开始需求集中安排。

批次是建议的依赖顺序，不是已完成状态或删减范围。P2先使用统一任务与库存服务，P3调用同一确认命令，不另建自动排产专用账目。

### 人工用杆量字段字典：统一输入总需求，后端只扣一次

以下是本轮统一的技术字段语义，不增加成材率配置或业务审批，不允许各成员自行选择“输入总量”或“输入净量”两套实现。

| 字段 | 读写与格式 | 固定语义及依据 |
| --- | --- | --- |
| `manualPlannedRodTon` | 人工输入的Decimal字符串；无需生产或待补依据时可为null | **本次仍需新加工铜丝部分的计划用杆总需求，尚未扣除铜杆现货和有效预期供料。**它不等于铜丝要求量，也不等于需要车间一补产的量；不能把已扣过库存的净量直接填进本字段 |
| `productionScope` | 随人工量一并传递、保存的依据快照 | 至少说明订单ID/整数订单版本、铜丝物料ID、原要求量、已实际完成及既有/本草稿成品分配依据、对应的`remainingWireTon`；区分已生效事实与本草稿拟分配量，不能把既有成品当新生产 |
| `productionScopeVersion` | 服务端当前范围的JSON非负整数 | 随订单/剩余生产范围一起读取；保存时对比当前版本，同时核对本草稿提出的范围快照。确认保存后，将本次人工量与实际采用范围、版本及操作依据一起留存，后续可追溯，不能只存一份会被覆盖的订单总量 |
| `rodStockUsedTon` | 后端输出的Decimal字符串，只读 | 本次需求使用的可用铜杆现货份额；重排时只把本次可替换旧需求原占用纳入重新核对，不释放或借用其他有效需求的预留 |
| `effectiveFutureSupplyTon` | 后端输出的Decimal字符串，只读 | 在相应用料时点前可兑现、尚未被其他需求承诺的有效供料份额；与现货分列，不增加实物库存 |
| `netNewRodTon` | **仅后端计算和返回**的Decimal字符串 | 按各用料时点及共同需求计算：总需求减本次可用现货、减有效供料后的净新增Φ8补产量，最小为0。同一现货/供料份额只扣一次，不允许客户端将该字段作为人工用杆输入或直接指定最终配料余额 |
| `plannedPlateTon` | 后端输出的Decimal字符串，只读 | 将同一确认用料范围的净新增杆量合并后，按`ceilKg(netNewRodTon × 1.05)`计算一次；按日拆分或多订单关联不再乘系数/取整 |

已有成品足够满足订单时，不要求填写`manualPlannedRodTon`，不因此制造生产任务。仅部分成品满足、增减量、成品分配/更正或实际完成情况改变了**仍需新加工范围**时，原人工量的范围依据标为需核对；用户在原草稿中人工重核并更新该字段及范围快照。新值可与旧值相同，但必须对应当前范围。系统不能按铜丝1:1或数量比例自动改算这一人工量；不新增确认按钮、业务评估回路或审批。

尚无用杆依据时，订单及已有真实事实仍可保存；只有需要新增生产的方案不能把未知量当0自动确认。S2-P01/P02返回缺项与当前范围，S2-P06在同一保存中校验范围及人工输入；范围变化冲突仍在原草稿处理。

旧原型或历史资料若记录的是已扣库存的净量，只能作为人工核对的历史来源，不能不经转换就按上述总需求语义再次扣现货。历史原值保留，正式接口不提供总量/净量二选一的开关，也不默默改变历史实际。

### 5.1 草稿契约：浏览器保留优先

### 5.2 一次确认必须保证的结果

1. **整单成品足够**：只保存成品归属/预留，不补造车间任务、铜板投入或铜杆产量；与后续S2-D02共用分配服务，而非让前端再发第二次分配确认。
2. **铜杆缺口提前补排**：车间二用杆日需要10吨、现货4吨时，提前安排可兑现的6吨，或明确同日先称重入库后领用；不是把4吨现货改成10吨。未来供料关系防重复承诺。
3. **铜板只算一次**：人工`manualPlannedRodTon`始终是当前尚需新加工范围的总用杆需求；后端扣除可用现货和有效供料一次得到`netNewRodTon`。按本次确认用料需求合并净新增杆量后，`ceilKg(netNewRodTon × 1.05)`；1.001吨→1.052吨，整公斤结果不额外加1公斤。原有效已安排供料不能再次折算，日拆分不能再乘系数或重复取整。铜杆/铜丝/铜板数量不得相互冒充。
4. **车间一统筹**：固定Φ8，只合并已知净需求与未来未开始安排，在物料、各供料时点及当日产能内集中、适当前移；不逐订单均摊、不为填满产能自动新增备库生产。
5. **同日顺序与两车间关系**：每车间一条线、一天可有多个顺序任务，两车间可服务不同订单。`sequenceNo`与供料先后关系表达日内顺序，不擅自引入分钟工时换算；检查顺序冲突和同日供料循环。新排未来任务不能放到已经过去的日期；历史实际补录走生产接口，不能用补排任务代替事实。
6. **重排保护实际**：有真实投入、领用、称重或已经开始的任务不被替换；保留原目标及差额，剩余量另排。重排只调整本次明确范围，更新同一需求的原有效预留/供料关系，不将原份额重复累加。
7. **当前数据重新校验**：在同一事务中检查订单/任务版本、物料/规格、有效产能、未占现货、未来供料承诺及先后。不足或变化返回409，保留客户端draft和逐项冲突；编辑/保存检查不是新增一轮业务评估。
8. **成本未齐**：合法分配及数量事实可成立，成本标待核算；已包含的材料/上游能源不能再次加。未来产出兑现时由生产事实事务和统一库存服务衔接承诺及现货预留，不能重复新增承诺或要求选来源批次。

交付明细由S2-D05按交付ID筛选或包含`items`返回；具体是否再拆单条只读URL属于查询实现选择，不另增一条业务命令。交付时服务端核销本单未交付份额并返回明细，不能让前端分别调用“交付保存”“库存出库”“成本扣减”拼接事务。

## 7. 与生产、能源、成本清单的唯一职责边界

| 业务事实/能力 | 对外命令归属 | 本清单及内部调用约束 |
