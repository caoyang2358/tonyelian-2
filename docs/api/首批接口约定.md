# 首批接口约定：设备档案查看与编辑

日期：2026-11-02；设计稿v0.1。目的：把目前只读的8台设备做成第一个真实保存、刷新可查、并发和更正可验证的业务功能。这里只设计接口，不编写业务Controller、DDL或假成功响应。

共同规则见[接口通用约定](接口通用约定.md)，全量范围见[系统一接口清单](系统一接口清单.md)。业务依据为需求基线12.1、12.2、3.2和数据库逻辑对象E01/G02。

## 1. 首批边界及交付顺序

| 顺序/编号 | 方法和路径（省略/api/v1） | 页面用途 | 现状 |
| --- | --- | --- | --- |
| 1 / BASE-04 | GET `/reference-data` | 设备表单的车间、工序、类型、单位及状态选项 | 待开发 |
| 2 / S1-E01 | GET `/equipment` | 当前设备列表；后续加后端筛选及扩展摘要 | 基础已实现 |
| 3 / S1-E02 | GET `/equipment/{equipmentId}` | 点击设备查看完整档案、版本和缺项 | 待开发 |
| 4 / S1-E03 | POST `/equipment` | 新增生产设备及扩展档案 | 待开发 |
| 5 / S1-E04 | PUT `/equipment/{equipmentId}` | 编辑共享允许字段和二期扩展，保存更正记录 | 待开发 |
| 6 / S1-E06 | GET `/equipment/{equipmentId}/changes` | 查看该设备新增/编辑/删除的留痕 | 待开发 |
| 7 / S1-E05 | DELETE `/equipment/{equipmentId}` | 无关联的误建档案，二次确认后删除 | 首批后置；完整关联检查就绪才开放 |

第一批先完成前6行，再决定是否具备开放删除的完整检查条件。供应商、合同、附件、测点配置、实时趋势、巡检维修和期限汇总在后续批次实现；它们仍在全量清单中，不因本次先做基础档案而删除。

一期设备继续使用同一`equipment_id/code`。只建立二期扩展，不复制8条新身份。初始设备缺失类型、日期或寿命时返回null/待补充，不根据名称或演示图自动回填事实。

## 2. BASE-04 公共选项

GET `/reference-data`，无请求体、无业务写入。建议返回：

| data字段 | 每项字段 | 来源及规则 |
| --- | --- | --- |
| `workshops[]` | `id,code,name,enabled` | 读取dim_workshop，ID字符串；不可把车间名当关联键 |
| `processes[]` | `id,code,name,workshopId,sequenceNo,enabled` | 读取dim_process；未配置返回[]，不按图例虚构库内ID |
| `units[]` | `id,code,name,category` | 读取dim_unit；用于测点等配置，不强迫设备文本参数使用同一套单位表 |
| `equipmentTypes[]` | `code,name` | 首批表单选项，见下；不是给现有设备自动分类 |
| `equipmentManagementStatuses[]` | `code,name` | IN_USE在用、STOPPED停用、SCRAPPED报废；允许档案实际状态待补充 |

首批类型选项建议：`MELTING_FURNACE`熔化炉、`HOLDING_FURNACE`保温炉、`CASTING_TRACTION`结晶牵引设备、`ROLLING_MILL`轧机组、`DRAWING_MACHINE`拉丝机、`DIAMETER_GAUGE`测径仪、`OTHER`其他生产设备。字典名称属于研发编码，后续可以扩展，不新增能源设施/辅助设备档案。

保存时重新校验车间/工序仍存在且可用，工序属于所选车间。空工序允许保存；选项接口失败必须显示错误，前端不能用硬编码ID继续写。

## 3. S1-E01 列表兼容和扩展

**当前真实结果**为`data.items`，含`id,code,name,workshopId,workshopName,responsiblePerson,enabled`，ID当前是JSON整数。当前前端已经兼容并转换为字符串。直接调用已有GET即可验证已有8台设备，不能把后续字段当作已上线。

后续建议增加可选查询：`keyword,workshopId,typeCode,managementStatus,enabled,page,pageSize`。默认全部生产设备，按车间编码、设备编码稳定排序；过滤和分页必须在后端实现后才显示为可用契约。

- 无分页参数时保留现有`data.items`结果，避免现有调用方只看到第一页。
- 明确传`page/pageSize`时才返回分页字段，采用通用分页约定；客户端不把当前页长度当total。
- 后续列表项可追加`typeCode,typeName,managementStatus,version`；不得以缺失类型过滤掉初始档案。
- `enabled`只是共享主数据的启用标记，不等于设备在线、正在生产或机械健康。管理状态、监测状态分别显示。

## 4. S1-E02 设备详情

GET `/equipment/{equipmentId}`。设备不存在404；扩展档案不存在时正常返回共享资料，不能因此404。

```json
{
  "id": "1",
  "code": "SMELT-FUR-01",
  "name": "1#熔化炉",
  "workshopId": "1",
  "workshopName": "车间1 · 铜杆生产",
  "responsiblePerson": null,
  "enabled": true,
  "profile": {
    "typeCode": null,
    "model": null,
    "processId": null,
    "installationLocation": null,
    "manufacturer": null,
    "factorySerialNo": null,
    "purchasedOn": null,
    "commissionedOn": null,
    "expectedLifeYears": null,
    "warrantyExpiresOn": null,
    "managementStatus": null,
    "technicalParameters": []
  },
  "version": 0,
  "missingFields": ["profile.typeCode"],
  "deletion": {
    "allowed": false,
    "blockers": [{"type": "SENSOR", "count": 1, "message": "该设备已关联测点"}]
  }
}
```

以上是示例data，不是固定ID、实际关联数量或数据库回填脚本。实际ID和关联数量必须查询。扩展尚未建立时，聚合版本返回0只是并发契约，不为这次GET写入任何数据。

`missingFields`只列基线必需但尚未补充的字段，不把全部可选资料都视为错误。责任人等未知返回null。删除检查尚未完整实现时`allowed=false`并说明暂不支持；不能直接返回true。

## 5. S1-E03/04 新增与编辑的字段

### 5.1 字段表

| 字段 | 类型/必填 | 说明及校验 |
| --- | --- | --- |
| `requestId` | UUID字符串，必填 | 同一提交重试沿用，数据库防重复 |
| `operatorName` | 非空字符串，必填 | 手填经办人，不建设登录 |
| `expectedVersion` | 非负整数，编辑必填 | 新增不传；首次补充旧档案为详情查询到的0 |
| `reason` | 字符串，编辑必填 | 说明重要更正原因；新增可不传 |
| `code` | 字符串，必填，最多64字符 | trim后非空，数据库唯一；已有设备编辑时必须保持原编码，不重新编身份 |
| `name` | 字符串，必填，最多100字符 | 设备名称 |
| `workshopId` | 正整数ID字符串，必填 | 引用已存在可用车间 |
| `responsiblePerson` | 字符串或null，最多100字符 | 责任人可后补，不用经办人自动填充 |
| `enabled` | 布尔，必填 | 共享启用标志；与管理状态分开 |
| `profile.typeCode` | 字符串，新增/编辑必填 | 引用类型选项；历史缺值可读，编辑时提示补齐 |
| `profile.model` | 字符串或null | 型号，可后补 |
| `profile.processId` | ID字符串或null | 存在且属于同一车间，不能因示意布局改变真实归属 |
| `profile.installationLocation` | 字符串或null | 安装位置 |
| `profile.manufacturer` | 字符串或null | 制造商名称；供应商关联在后续批次独立维护 |
| `profile.factorySerialNo` | 字符串或null | 出厂编号，与设备唯一编码分开 |
| `profile.purchasedOn` | 日期或null | 购置日；缺失不补今天 |
| `profile.commissionedOn` | 日期或null | 投用日；缺失不推算寿命 |
| `profile.expectedLifeYears` | 正整数或null | 预计年限；正整数为首批研发字段约定，不额外给企业设一个默认寿命 |
| `profile.warrantyExpiresOn` | 日期或null | 质保到期；独立于维保合同起止日期 |
| `profile.managementStatus` | IN_USE/STOPPED/SCRAPPED或null | 基于实际管理记录，不从enabled或离线状态自动推定 |
| `profile.technicalParameters[]` | 数组，可为[] | 类型差异参数，格式见下；不是传感器阈值 |

除共享表明确长度外，扩展文本长度在首批DDL/DTO中同步确定；不能只前端校验、后端无限截断。日期字段需合法，不自动增加基线未确认的历史采购顺序或设备启停限制。

技术参数项：`key,label,valueType,value,unitLabel`。`key`在本设备中唯一；`valueType`为STRING/DECIMAL/INTEGER/BOOLEAN；数值使用十进制字符串、布尔使用JSON布尔，单位为可选展示文本。例如额定功率只是设备资料，不把它自动当作实际能耗。不同类型可用不同参数集合，首批不额外建设通用表单设计器。

    "typeCode": "OTHER",

    "installationLocation": null,

### 5.3 编辑请求及并发

PUT `/equipment/{equipmentId}`，使用上述完整设备字段，额外提供`expectedVersion`及非空`reason`。这里约定全量表单保存：可空字段传null代表明确清空，数组传[]代表清空；字段遗漏返回400，不能悄悄把遗漏当作清空。只读字段如`id/workshopName/version/missingFields/deletion`不接受写入。

- `code`必须与现值相同；名称、车间、责任人、enabled经统一主数据服务更新，扩展字段写二期档案。
- 已有测点/工序等关联的车间变更要重新检查归属一致性；冲突时409，不能自动搬迁测点去配合页面。
- 事务读取并锁定设备聚合，校验当前版本。两个客户端都读到0，第一个保存变为1，第二个仍提交0必须409；失败不写一半主表或留痕。
- 无扩展时第一次有效保存建立一条扩展；不因表单打开或查询创建资料。
- 保存主资料、扩展、版本和修改前后快照一起成功；错误时全部回滚。
- 原始日期和寿命更正保存原因，期限展示后续按真实字段重新推算，不手工维护一个易过期的“剩余天数”。

## 6. S1-E06 更正记录

GET `/equipment/{equipmentId}/changes?page=1&pageSize=20`，按录入时间倒序，返回分页结构。

每项至少包含`id,operation,before,after,reason,operatorName,recordedAt,requestId,versionBefore,versionAfter`。`operation`为CREATE/UPDATE/DELETE；新建前值null，删除后值null。不存在的历史不补造，旧8台在二期建设前没有更正记录时可返回[]。

更正留痕不提供“编辑/删除留痕”接口。误建删除时保留原身份及必要快照，历史查询不依赖该设备主行必须仍存在；如果对象和留痕都不存在则404。

## 7. S1-E05 误建删除

DELETE `/equipment/{equipmentId}`，需要前端二次确认，发送：

```json
{
  "requestId": "9b0f49e9-b3c1-49e4-9cc7-62f7c83d5fa9",
  "operatorName": "示例经办人",
  "reason": "误建且无业务关联",
  "expectedVersion": 1,
  "confirmed": true
}
```

服务端在同一事务再次核对版本及测点/生产/巡检/维修/合同/知识/布局等已建模块的业务引用，不能只相信前端传来的“无关联”。存在关联返回409及可读blockers，保留档案，可走正常管理状态编辑。

本设备自身扩展和审计快照不是为了阻止所有删除而额外制造的业务关联；处理自有扩展时保留审计依据，不级联删除其他业务。后续模块新建关联时必须接入关联检查和必要约束；检查不齐时保持此入口不可用。

成功返回`{id,deleted:true}`。成功后重试相同requestId仍返回首次结果，不能因主行已删就误报第一次未成功；无历史成功请求的未知ID返回404。

## 8. 首批数据变更与成员分工

- 复用`dim_equipment/dim_workshop/dim_process/dim_unit`。主数据写入白名单只含本接口允许的共享字段；`equipment_usage`由服务端固定PRODUCTION，不让表单切到能源设施/辅助设备。
- 新建/落实`p2_equipment_profile`、设备聚合版本与`p2_change_log`，幂等持久化设计随任务落实。仅实施本批需要的结构，不先创建全量37个逻辑对象。
- 不更改一期采集表、能源汇总、迁移历史，不在现用库做开发试验。迁移统一放二期Flyway目录，用后续版本修正。
- 建议一位全栈成员负责这整条设备功能，另一位审查；其他成员同时开展订单/库存基础设计。不是一人只写Controller、另一人等所有接口完成才开始页面。

## 9. 首批完成验收

| 场景 | 预期 |
| --- | --- |
| 初次打开8台基础设备 | 沿用原ID/编码；缺类型、日期和责任人显示待补充 |
| 保存档案后刷新、重启再查 | 主资料和扩展均可查回；version递增 |
| 不同设备类型的技术参数 | 各自保存，不给所有设备强塞同一组参数 |
| 重复编码新增 | 409，主表/扩展不留下半条 |
| 同一新增请求超时重试 | 只出现一台新设备 |
| 两客户端基于同版本编辑 | 先成功者保留，后提交者409，不能静默覆盖 |
| 购置/寿命/状态更正 | 能查前后值、原因、时间和经办人，缺值仍保持null |
| 错误车间/工序或编辑原编码 | 400/409及明确字段/冲突提示；不重写原身份 |
| enabled=false或无实时数据 | 不自动推断报废、机械故障或已知综合评级 |
| 有关联设备误建删除 | 拒绝删除；无关联且二次确认的才允许；删除留痕保留 |
| 只查询或打开表单 | 不创建扩展、不递增版本、不产生更正记录 |

完成定义：页面、接口、迁移一起交付，经过上述相关场景验证，并由另一人审查；当前清单完成不等于这批业务已实现。
