# 系统一 · 运维管理页面接口文档

日期 2026-11-03。版本 v0.1，开发与联调草案。覆盖提醒、巡检、维修、概览四个页签及其详情和操作。沿用清单中的接口编号、路由、业务动作和状态转换。下文新增的 DTO 字段、枚举和统计窗口细节均为拟定契约。运维业务接口均待开发，设备选择可复用已实现的基础设备列表。[系统一接口清单](系统一接口清单.md) · [需求基线第 12—13 节](../需求基线.md)

## 1. 请求与响应

接口使用 `/api/v1` 前缀，下文路径均省略此前缀。JSON 成功返回 HTTP 200 和 `{code:"OK",message,data,timestamp}`。集合返回 `{items,page,pageSize,total}`，默认第 1 页、每页 20 条，最多 100 条。除既有设备列表兼容字段外，业务 ID 用十进制字符串。时间使用含偏移的 ISO 8601，业务时区为 Asia/Shanghai。监测值、阈值用十进制字符串，计数和版本用 JSON 整数，缺项返回 `null`。

下表 `W` 为 `requestId, operatorName`，`U` 为 W 加上所操作对象的 `expectedVersion`。经办人手填。超时重试沿用原请求 ID，变更内容后再次提交使用新 ID。成功后用响应中的新版本继续操作。重要更正和需说明的动作保存原因、经办人、录入时间及来源依据。[接口通用约定](接口通用约定.md)

## 2. 提醒页签

| ID | 方法与路径 | 输入 | 响应 data 与页面用法 |
| --- | --- | --- | --- |
| S1-A01 | GET `/alert-events` | `equipmentId?, sensorId?, parameterId?, eventState?, handlingState?, from?, to?, page?, pageSize?` | 分页事件摘要。默认按触发时间、ID 倒序，行内显示设备测点、触发时间、实际恢复或结束、人工处理和关联工单 |
| S1-A02 | GET `/alert-events/{eventId}` | 事件 ID | 事件摘要加触发证据、原规则快照、读数来源、当前版本和关联维修状态 |
| S1-A03 | POST `/alert-events/{eventId}/handling-records` | U，`action` 为 `ACKNOWLEDGED` 或 `DEFER_REPAIR`，`reason` | `handlingRecordId, handlingState, version, updatedAt`。仅变更人工处理状态，事件事实和维修状态分别读取 |
| S1-A04 | GET `/alert-events/{eventId}/handling-records` | `page?, pageSize?` | 分页历史，每行 `handlingRecordId, action, reason, operatorName, recordedAt`。保留每次动作 |
| S1-P01 | GET `/sensors` | `enabled=true` 及离线状态筛选，设备和分页可选 | 复用测点列表，展示设备、测点编码、最近采集时间及监测状态。缺采集、过期和离线分别展示 |
| S1-P02 / P06 / P09 | GET `/sensors/{sensorId}`、GET `/sensors/{sensorId}/parameters`、GET `/sensor-parameters/{parameterId}/latest` | 测点或参数 ID | 跳转到共享测点资料、参数和当前读数。事件触发值取 A02 的历史证据 |
| S1-T01 | GET `/equipment-deadlines` | `equipmentId?, workshopId?, reminderType?, expiryState?, page?, pageSize?` | 分页期限行，含设备或合同身份、类型、到期日、剩余天数、计算状态、缺资料原因 |
| S1-T02 / T03 | GET / PUT `/reminder-settings` | GET 无。PUT 传 U、`warrantyLeadDays, maintenanceLeadDays` | 查询及保存两种提前天数，均为非负整数，默认各 30 天。设置属于共用接口，页面设置入口若展示则复用 |
| S1-R01 | POST `/repair-orders` | W，`sourceType:"ALERT_EVENT", sourceId:eventId` | 人明确选择报修时创建草稿并打开详情 |

拟定事件摘要字段为 `eventId, equipmentId, equipmentName, sensorId, sensorCode, parameterId, parameterCode, startedAt, triggeredAt, recoveredAt, endedAt, endReason, eventState, handlingState, repairOrderIds, version`。详情补 `triggerValue, unitCode, sourceReference, ruleVersionId, ruleSnapshot`。规则快照包含触发时阈值、判断模式、有效持续时长等依据。实际恢复时间只用于自然恢复。规则变化结束使用 `RULE_CHANGED`，保留历史快照并在下一有效数据按新规则判断。短暂超限按普通持续条件处理，关键参数可按配置立即提醒。同一持续过程仅一条事件，已存在的维修单继续走原流程。

期限根据业务日期计算。寿命使用投用日期加预计使用年限，距到期不足一年提示评估。质保、维保按各自提前量显示，到期后继续提示。资料缺失时日期或剩余天数为 `null`。查看对象可复用设备档案 S1-E02 和合同详情 S1-C02。

## 3. 巡检页签

| ID | 方法与路径 | 输入 | 响应 data 与页面用法 |
| --- | --- | --- | --- |
| S1-I01 | GET `/inspections` | `equipmentId?, result?, from?, to?, page?, pageSize?` | 分页记录。按巡检实际时间、ID 倒序，显示设备、时间、巡检人、结果和报修关联 |
| S1-I02 | GET `/inspections/{inspectionId}` | 巡检 ID | `inspectionId, equipmentId, inspectedAt, inspectorName, content, result, description, repairOrderIds, version` |
| S1-I03 | POST `/inspections` | W，`equipmentId, inspectedAt, inspectorName, content, result, description?` | 巡检详情及版本。校验设备、时间、巡检人、巡检内容和结果 |
| S1-I04 | PUT `/inspections/{inspectionId}` | U、`reason`，提交需维护的巡检资料 | 更新后的详情、版本和 `changeLogId`。已有工单继续引用创建时的巡检来源快照 |
| S1-R01 | POST `/repair-orders` | W，`sourceType:"INSPECTION", sourceId:inspectionId` | 巡检发现异常后，由人选报修并取得草稿 ID |

巡检结果拟定为 `NORMAL / ABNORMAL`。记录实际发生时间 `inspectedAt` 和服务器录入时间 `recordedAt`，巡检人与录入经办人可以不同。设备选择复用 S1-E01。初始接口的数字 ID 在构造新接口请求前转为字符串。保存巡检异常后可展示报修入口，创建草稿需单独的人工作用。

## 4. 维修页签与工单详情

| ID | 方法与路径 | 输入 | 响应 data 与页面用法 |
| --- | --- | --- | --- |
| S1-R01 | POST `/repair-orders` | W，`sourceType` 取 `ALERT_EVENT / INSPECTION / MANUAL`。有来源时传 `sourceId`，手工来源时传 `equipmentId` | `repairOrderId, status, sourceSnapshot, editableFields, version`。初始为 `DRAFT` |
| S1-R02 | GET `/repair-orders` | `equipmentId?, status?, sourceType?, from?, to?, page?, pageSize?` | 分页工单摘要，含单号、设备、来源、首次提交时间、状态、待处理阶段及版本 |
| S1-R03 | GET `/repair-orders/{repairOrderId}` | 工单 ID | 工单摘要、历史来源快照、可编辑补充内容、照片引用、当前可操作项、每轮动作摘要 |
| S1-R04 | PUT `/repair-orders/{repairOrderId}` | U，故障说明 `description`、异常补充 `supplement?`、报修人 `reporterName`、`photoAttachmentIds[]`，必要更正原因 | 保存草稿或待补充资料。返回同一工单详情、新版本和必要审计依据 |
| S1-R05 | POST `/repair-orders/{repairOrderId}/submissions` | U，必要提交说明 | 正式提交或补充后重提。返回新状态、动作 ID、版本及时间 |
| S1-R06 | POST `/repair-orders/{repairOrderId}/reviews` | U，`result`，退回补充、无需维修和重复关闭时必填 `reason` | 记录审核动作并返回新状态、动作 ID、版本及时间 |
| S1-R07 | POST `/repair-orders/{repairOrderId}/repair-results` | U，`performedAt, description, attachmentIds?` | 保存本轮实际维修结果并返回新状态、动作 ID、版本及时间 |
| S1-R08 | POST `/repair-orders/{repairOrderId}/acceptances` | U，`result, acceptedAt, reason` | 保存本轮人工验收并返回新状态、动作 ID、版本及时间 |
| S1-R09 | GET `/repair-orders/{repairOrderId}/actions` | `page?, pageSize?` | 分页历史，拟定每行含 `actionId, actionType, result, previousStatus, nextStatus, occurredAt, recordedAt, operatorName, reason, attachmentIds`，按动作顺序还原流转 |

拟定工单摘要字段为 `repairOrderId, orderNo, equipmentId, equipmentName, sourceType, sourceId, status, createdAt, firstSubmittedAt, completedAt, version`。事件来源带入设备、测点、参数、发现时间、触发值和单位。巡检来源带入设备、时间、巡检结果和相关内容。用户描述与来源快照分开保存。维修动作写入应在一个事务内校验当前状态和版本、保存本轮历史并推进工单；同一请求重试返回同一动作。

| 当前状态 | 动作及入参值 | 保存后状态 |
| --- | --- | --- |
| `DRAFT` / `RETURNED_FOR_INFO` | R04 保存资料 | 保持原状态 |
| `DRAFT` / `RETURNED_FOR_INFO` | R05 正式提交，校验故障说明、报修人员及有效附件 | `REVIEW_PENDING`，保留首次提交时间 |
| `REVIEW_PENDING` | R06 `APPROVE` | `IN_REPAIR` |
| `REVIEW_PENDING` | R06 `RETURN_FOR_INFO` | `RETURNED_FOR_INFO` |
| `REVIEW_PENDING` | R06 `NO_REPAIR` 或 `DUPLICATE` | `CLOSED`，记录具体关闭原因 |
| `IN_REPAIR` | R07 保存本轮实际维修结果 | `ACCEPTANCE_PENDING` |
| `ACCEPTANCE_PENDING` | R08 `PASS` | `COMPLETED` |
| `ACCEPTANCE_PENDING` | R08 `FAIL` | `IN_REPAIR`，同一工单继续下一轮 |

照片可选。先取得工单 ID，再通过 S1-F03 上传并关联，工单保存时引用有效的附件 ID。已有附件能力沿用以下共享路由。

| ID | 方法与路径 | 输入及输出 |
| --- | --- | --- |
| S1-F01 | GET `/attachments` | `ownerType, ownerId, fileKind?, page?, pageSize?`，返回已关联附件分页及版本 |
| S1-F02 | GET `/attachments/{attachmentId}` | 返回附件元信息、关联对象及受控查看入口 |
| S1-F03 | POST `/attachments` | multipart 含 W、`file, ownerType, ownerId, fileKind`，返回附件 ID、媒体类型、大小和版本。报修照片拟用 `ownerType=REPAIR_ORDER, fileKind=PHOTO` |
| S1-F04 | GET `/attachments/{attachmentId}/content` | `download?`，成功返回文件流和媒体类型，错误沿用 JSON 信封 |
| S1-F05 | PUT `/attachments/{attachmentId}/content` | 共用附件替换能力，multipart 含 U、`file` 和必要原因，返回更新后元信息并保留原附件 ID。页面采用该操作时遵守工单阶段和来源证据保护 |

## 5. 概览页签

S1-M01 `GET /maintenance-overview` 接受 `workshopId?, equipmentId?, from, to`，返回筛选范围、统计截止时间、计数、样本量和按设备分组数据。以下字段及窗口为拟定联调口径，服务端在响应中说明所用口径。按自然日选择时换算为本地起始时刻（含）至末日次日零时（不含）。

| 拟定字段 | 口径 |
| --- | --- |
| `inspectionCount, alertEventCount` | 分别按实际巡检时刻、事件触发时刻计数。同一持续异常计一次 |
| `pendingRepairCount` | 当前正式工单中待审核、待补充、维修中、待验收的数量，拟按首次提交落入筛选范围筛选 |
| `completedRepairCount` | 按验收通过时刻统计范围内完成量 |
| `averageHandlingSeconds, handlingSampleCount` | 同一完成样本的首次正式提交到验收通过时长均值及样本量，均值拟返回十进制字符串，无样本为 `null` |
| `equipmentReportCounts[]` | 每台设备首次正式提交落在范围内的工单数，可附范围内完成数。补充后重提或重复请求不再计数 |
| `deadlineReminderCount` | 按设备范围和当前期限设置生成的提醒数量，附统计日期 |

## 6. 异常反馈与联调

| 场景 | 后端结果及页面处理 |
| --- | --- |
| 缺字段、日期范围无效、动作枚举无效、附件格式或大小校验失败 | 400 `VALIDATION_ERROR`，按 `fieldErrors` 展示，保留用户已填内容 |
| 工单、来源对象或文件不存在 | 404 `NOT_FOUND`，提示刷新。附件元信息与文件内容可分别报告缺失 |
| 版本变化、操作与工单阶段不符 | 409 `VERSION_CONFLICT` 或 `STATE_CONFLICT`，刷新详情及动作历史，保留可重新提交的输入 |
| 同一请求标识携不同业务内容 | 409 `IDEMPOTENCY_CONFLICT`。重试沿用原内容，修改后创建新的提交标识 |
| 读取失败或来源数据缺失 | 接口失败与有效的空列表分开。真实缺测、期限资料缺失、没有处理时长样本分别显示，读取故障可重试 |

联调验收覆盖以下链路。[需求基线 AC19、AC20、AC48](../需求基线.md)

1. 普通短时超限未达到持续条件。达到条件后只出现一条事件。自然恢复后再次达到条件新增事件。变更阈值仅结束受影响旧事件并保留原证据，原工单状态仍由维修动作推进。
2. 已知悉和暂不报修分别留痕。巡检异常或事件进入草稿时，正式报修次数保持原值。保存资料和照片后人工提交，次数增加一次。相同请求重复提交只产生一次动作。
3. 验证审核退回、补充后重提、维修验收失败、同单再次维修并通过。R09 可还原各轮记录，概览以首次提交到验收通过为一条处理样本。
4. 审核以无需维修或重复关闭，保留关闭原因及来源记录。两个客户端并行推进同一版本时，后提交的冲突请求返回当前状态及版本。
5. 验证测点无数据、已确认离线、期限日期缺失、暂无完成样本以及文件不可读，页面分别显示对应结果。

联调依赖设备身份、测点与规则版本、期限计算、附件服务以及二期事件和工单记录。正式异常由服务端读取采集证据判断，演示数据在开发测试环境准备。
