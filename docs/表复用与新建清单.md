# 二期表复用、扩展与新建清单

日期：2026-11-02。状态：业务数据设计草案，业务表尚未建表；工程初始化另有技术元数据表p2_project_info。

完整表名、核心关系、分批开发及队员查询示例见[数据库逻辑表设计与成员使用指南](数据库逻辑表设计与成员使用指南.md)。一期源码12张表中11张用于复用，旧分时价表仅参考；二期列出37个可调整的逻辑存储对象，尚非最终物理表数量。

## 1. 推荐组织方式

二期前后端独立，数据库可以在同一个MySQL库中保留一期表，增加二期扩展和业务表。建议二期自有表统一 `p2_` 前缀。开发阶段每人使用独立开发库，共同测试时使用结构一致的测试库。

一期已有主数据保持同一身份，二期补充信息通过已有ID关联；新增业务由二期自己的表保存。下面表名是设计建议，不表示已生成或执行DDL。

## 2. 按功能划分

| 功能 | 复用已有表 | 二期扩展或新建 | 读写边界 |
| --- | --- | --- | --- |
| 车间与设备档案 | `dim_workshop`、`dim_equipment` | `p2_equipment_profile`，供应商、合同、附件及关联表 | 已有设备沿用 `equipment_id`；名称、车间、责任人等已有字段在共享主表统一维护，设备类型、型号、投用/购置、质保寿命等新字段放扩展表 |
| 测点、参数及配置 | `dim_sensor`、`dim_sensor_parameter`、`dim_unit`、`dim_process` | 持续异常规则、规则版本、异常事件 | 编码、名称、设备归属、单位等主数据按约定维护；二期持续时长、规则版本和事件状态独立，不重复建立相同身份 |
| 最新值与历史趋势 | `ads_parameter_monitor`、`ods_sensor_data` | 异常引用及必要展示配置 | 读取既有采集数据，不在二期重复造一套采集历史；新增配置不表示一期模拟程序已会发送新增测点 |
| 巡检、维修、知识、组网 | 关联既有设备/测点ID | `p2_inspection`、`p2_repair`、处理轮次、知识、布局等 | 二期读写自有业务记录；瞬时限值状态不能当成持续异常或维修结果 |
| 客户订单、产能、计划及库存 | 关联既有车间等身份 | 订单、任务、任务订单关联、产能日历、物料、预留及库存流水等 | 二期自有；一次确认保存计划和预留，保持数量及事务一致 |
| 实际投入、称重、交接、分配及交付 | 关联车间、任务等身份 | 投料、称重、订单产出归属、领用交接、成品分配及交付记录 | 二期合格产量来自新称重事实，事实和相应库存变化一起保存 |
| 能源总量与价格 | `dim_sensor`、`dim_energy_type`、`dws_energy_hour/day` | `p2_energy_price`、核算来源引用 | 读取对应车间/表计的消耗及质量；二期维护自己的简化生效单价，不覆盖一期分时价 |
| 铜杆及公共成品成本、订单盈亏 | 读取实际用能、生产和库存来源 | 库存成本、归属分摊、核算结果及更正记录 | 二期自行归集和补算，保留来源；不直接使用旧能源日表的成本作为订单成本 |

## 3. 用设备档案理解“扩展”

静态MySQL设备表已有 `equipment_id`、`equipment_code`、`equipment_name`、`workshop_id`、`responsible_person`、`enabled`、`equipment_usage` 等。

二期可以用 `p2_equipment_profile.equipment_id` 关联 `dim_equipment.equipment_id`，补充型号、设备类型、购置/投用、质保及预计使用年限等。设备页面由二期后端组合查询共享基础资料和扩展资料。

已有基础字段直接使用同一来源，新增档案字段放扩展；一份合同覆盖多设备时使用关联表。新增设备建议由二期统一主数据服务登记共享设备身份，再保存档案扩展；已有编码及ID保持稳定，不再复制一套相同设备身份。

关联键类型需与现有键一致，必要关系可以配置外键；具体约束和删除行为在实际结构核实后确定。[MySQL外键说明](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html)

## 4. 共享表的写入约定

| 数据类别 | 写入归属 |
| --- | --- |
| 原始采集、最新值及一期能源汇总 | 既有采集/聚合链路写，二期主要读取 |
| 车间、设备、测点及参数基础字段 | 列出二期允许维护的字段，统一通过主数据服务写入，保存更正记录；涉及一期写入同一字段时先统一负责人和规则 |
| 二期设备扩展和业务事实 | 二期负责写入，其他业务模块经过统一入口调用 |
| 表结构及数据迁移 | 团队统一编号和审查，先在开发/测试库验证，再安排目标环境执行 |

“二期独立工程”不等于全部既有表只能读；是否可写取决于具体业务和字段归属。改已有表结构与编辑已有记录是不同操作，分别管理。新增设备/测点也须维护已有唯一约束和关联。

## 5. 不同阶段的数据不能混用

- `dws_energy_day.production_quantity` 不作为二期订单产量；二期使用实际称重记录，避免跨电/水/煤气重复累加产量。
- 一期 `dim_energy_tariff` 的分时价和 `dws_energy_day.cost` 不直接替代二期确认的能源单价及订单成本。
- 参数瞬时限值、持续异常事件、人工报修及维修结果分别记录。
- 表计或成本来源缺失时沿用待统计/待核算，不用零替代。

## 6. 开发前真正要完成的工作

1. 获取实际MySQL仅结构资料，核对现有表、字段、类型、索引和约束。
2. 将每个二期字段标为“直接复用、共享主数据可维护、扩展、新建”，列清写入口和负责人。
3. 确定完整的新表和关系图、业务接口及事务边界，再生成二期MySQL迁移。
4. 迁移只管理约定对象。若采用Flyway，独立目录及历史表需显式配置，例如 `p2_flyway_schema_history`；首次接非空库的迁移配置也需在开发库验证。[Flyway历史表设置](https://documentation.red-gate.com/flyway/reference/configuration/flyway-namespace/flyway-table-setting)
5. 不整份重放一期初始化：现有MySQL V1脚本含 `DROP TABLE`；二期应编写自己的增量脚本，不执行旧清库初始化或修改一期迁移历史。

本清单没有实施现用库连接、建表或数据更改，也没有将草案表名当作最终DDL。
