## 1. 四级来源定义

本文用四个级别描述每张表的数据，避免用「真的/假的」这种容易含混的说法：

| 级别 | 含义 | 可信度 | 可否直接清空 |
|---|---|---|---|
| **A｜一期源码定义** | 从一期仓库 `db/migration-mysql/V1__mysql_schema.sql` 与 V2 元数据抄录，编码、名称、归属照原样 | 编号真实存在，但**未与现场核验** | ❌ 不能清，清了系统没有主数据 |
| **B｜联调造数** | 由 `scripts/seed_demo_readings.py` 等脚本按公式生成 | 数值无业务依据 | ✅ 可按标记清除 |
| **C｜人工录入** | 通过系统界面/接口真实创建，内容为编造 | 路径真实、留痕真实、内容不真实 | ✅ 可逐条删除 |
| **空白** | 该字段本应有值但未提供 | 系统如实显示「待补」，不填默认值 | — |

**关键点：A 类不等于「真实数据」。** 我们从未连接过一期的生产库，也没有到车间核对过探头数量。一期上线后可能新增了设备、改了名称、停了产线，这些我们都不掌握。

### 1.1 追溯链条：哪一层可校验，哪一层断了

被问「这个编码哪来的」时，能追到哪一步要说得清，否则容易被当成「编的」：

| 层 | 来源 | 可校验程度 |
|---|---|---|
| **表结构**（12 张表） | 一期仓库 `db/migration-mysql/V1__mysql_schema.sql`，已提取为 `database/dev/001_phase1_schema_snapshot.sql` | ⭐⭐⭐ 文件头记录了源文件 **SHA-256**（`a63b94efdb47…`），可校验 |
| **设备编码 / 名称 / 车间 / 测点** | 一期仓库同目录下的 **V2 元数据**，手工摘录进 `database/dev/002_demo_metadata_seed.sql`（2026-11-02 提交 `6a50fe0`） | ⭐ 只有一句注释 `copied from phase1 V2 metadata`，**无原文件副本、无 SHA** |
| **读数 / 合同 / 供应商 / 附件** | 本仓库脚本与页面录入 | — 明确为联调造数，见 §2、§4 |

**结论：结构可校验，数据只能追溯到「来源文件」，不能追溯到「源数据」。**

一期源码在本机是以压缩包形式存在的副本（目录名形如 `Git_NTP_TYL_Mid-main-<commit>`），**从未进入本仓库，任何分支都没有**；本机现已无该目录。要复核设备编码是否与一期一致、是否全量，只能重新取得一期源码或接入一期只读库。

**版本口径需注意**：快照实际取自 `bea8047f…`（见 `database/dev/README.md`），而《需求基线》《当前开发约定》指定的基线是 `b8f1231c…`，两者差异**未比对**。对外表述应为「取自当时在跑的那份部署源码」，不要说成「取自指定基线」。

## 3. 模拟数据与真实数据的对应关系

这是评审最关心的部分：**换掉数据源时，字段怎么对、代码要不要改。**

### 3.1 原始读数 `ods_sensor_data`（B 类，需整体替换）

| 字段 | 当前（模拟） | 接入真实采集后 | 是否需改代码 |
|---|---|---|---|
| `sensor_code` | `TEMP-001` 等 10 个一期编码 | **保持不变**，采集器按同一编码上报 | ❌ |
| `parameter_code` | `temperature` / `pressure` / `level` / `speed` / `diameter` / `tension` | **保持不变** | ❌ |
| `collect_time` | 每 3 分钟一条，从 22:24 到 23:21 严格等间隔 | 采集器实际上报时间（会有缺条、抖动） | ❌ |
| `value_num` | `1090 + 12×sin(i/3) + rand(-2,2)` | 传感器实测值 | ❌ |
| `source_unit` | `℃` / `Pa` / `%` 等 | 采集器上报单位，需与 `dim_unit` 对齐 | ❌ |
| `quality_code` | 硬编码 `GOOD` | 采集器质量码（GOOD/BAD/UNCERTAIN） | ❌ |
| `source_system` | `DEMO-SEED` | 改为采集系统标识，如 `PHASE1_COLLECTOR` | ❌ |
| `source_record_id` | 脚本生成的序号 | 采集器消息 ID，用于幂等去重 | ❌ |

**结论：读数层不需要改代码。** 采集通道接上后，只要按 `sensor_code + parameter_code + collect_time` 写入，页面、历史查询、最新值快照全部自动跟上。

**当前模拟数据的实际覆盖范围（避免误以为「每个测点都有数据」）**：

| 项 | 实际值 |
|---|---|
| 有读数的测点 | **仅 1 个**：`TEMP-001` / `temperature`（10 个测点中另外 9 个一条都没有） |
| 条数 | **20 条**，`2026-11-04 22:24:28` → `23:21:28`，严格每 3 分钟一条 |
| 取值范围 | 1077 ~ 1102 ℃（公式 `1090 + 12×sin(i/3) + rand(-2,2)`，随机种子固定 `20261104`，可重放） |
| 质量码 | 18 条 `GOOD` + 2 条 `UNCERTAIN`（脚本故意夹入，用于验证质量列） |
| 来源标记 | `source_system='DEMO-SEED'`，可整批清除 |

演示读数**可重放**：清空后执行 `python scripts/seed_demo_readings.py` 即可重新灌回同样的 20 条，所以交付前清空不会造成不可恢复的损失。

这也解释了测点列表里 `TEMP-001` 显示「数据过期」的原因：数据停在 11-04 23:21，而演示脚本只灌了一批就停了。**这是造数停了，不是设备断采。**

## 4. 如何识别与清理演示数据

### 4.1 可按标记定位的

```sql
-- 测点（10 条）
SELECT sensor_code, data_source FROM dim_sensor WHERE data_source = 'DEV_DEMO_METADATA';

-- 读数（20 条）
SELECT sensor_code, collect_time, value_num FROM ods_sensor_data WHERE source_system = 'DEMO-SEED';
```

### 4.2 只能按编码/时间识别的

| 对象 | 识别方式 |
|---|---|
| ~~`EQUIP-DEMO-002`~~ | **已于 2026-11-12 10:44 通过系统删除**（变更记录 `change_log_id=496`，原因「删除测试设备」），当前库内已无该设备 |
| 8 台一期设备 | 编码属于一期种子名单，**不可删** |
| 供应商/合同 | 全库仅 1 条，按 ID 定位 |
| 变更记录 | 按 `recorded_at` 时间段筛选 |

### 4.3 清理注意

- `ods_sensor_data` 被写入过的测点，其编码按 S1-P05 规则**被冻结**，不能再物理删除该测点。`seed_demo_readings.py` 当初特意选了要长期保留的 `TEMP-001` 灌数。
- 设备删除走安全删除：先查 10 张关联表，任何一类计数 > 0 即拦截 409。**当前 8 台设备里可删的只有 3 台：`HOLD-FUR-01`、`DRAW-01`、`DRAW-02`**；其余 5 台挂着测点（`CAST-01`、`ROLL-01`、`DRAW-03`、`GAUGE-02` 各 1 类，`SMELT-FUR-01` 为测点 + 监控点 2 类）。演示单据删除后，`CAST-01` 的合同类关联也随之解除。

## 5. 接入真实数据的操作顺序

不需要改代码，按这个顺序做：

1. **拿到一期只读连接**，核对 `dim_workshop` / `dim_equipment` / `dim_sensor` / `dim_sensor_parameter` 的编码是否与开发库一致；不一致以现场为准，差异列清单。
2. **补齐设备档案空白**：管理状态、责任人、型号、厂家、购置/投用/质保日期。这一步做完，期限看板才真正可用。
   - **注意：这些字段一期数据库里没有**。一期 `dim_equipment` 全文只有 7 个业务字段——`equipment_code`、`equipment_name`、`workshop_id`、`responsible_person`、`enabled`、`equipment_usage`（+ 两个时间戳）。型号、厂家、出厂编号、安装位置、购置/投用/质保日期、预计寿命、设备类型、管理状态**在该表中均不存在**，是二期 `p2_equipment_profile` 新建的。
   - 因此**即使拿到一期只读权限也补不出这些值**，必须取线下来源：设备台账/铭牌（型号、厂家、出厂编号、安装位置）、采购合同与验收单（购置日、投用日、质保到期、预计寿命）、车间提供（责任人、在用/停用/报废）、工艺部门提供（工序主数据）。
   - 一期有列但本身为空：`responsible_person`（8 台为空）；一期有表但无数据：`dim_process`（0 条）。
3. **补 `dim_process` 工序表**，否则编辑设备时「所属工序」下拉是空的。
4. **配置阈值与采样周期**，生成规则版本 v1，异常事件才会开始产生。
5. **接通采集通道**，按 `3.1` 的字段映射写入 `ods_sensor_data`，`source_system` 换成真实标识。
6. **替换供应商/合同/附件**为真实台账。
7. **保留全部变更记录**，不清理。

    **从这张表能直接读出三件事**，不需要推断：
    1. 车间1 的四台设备**类型各不相同，却全部是「1#」**——所以 `#` 不是车间内的统一序号，不可能按车间顺序排 1/2/3/4
    2. 序号只在**同类设备内**连续：拉丝机 1#/2#/3#，是唯一连续的一组
    3. 车间与序号无对应关系：车间1 全是 1#，车间2 同时有 1#、2#、3#
  - **它同时说明了「系统对名称没有任何约束」**：联调期曾有一台 `EQUIP-DEMO-002`「2#测试设备」，名称与类型（结晶牵引）都对不上，系统照样存下、照样参与列表；该设备已于 2026-11-12 删除，但它证明了名称只是一个自由文本字段
  - **`#` 的作用就是给设备编号，正式载体是 `equipment_code` 而不是名称**：编码结构一律为「工艺缩写 + 两位序号」，名称里的 `#` 只是把这个序号用口语再写一遍。8 台逐台吻合：`SMELT-FUR-01`↔1#、`HOLD-FUR-01`↔1#、`CAST-01`↔1#、`ROLL-01`↔1#、`DRAW-01/02/03`↔1#/2#/3#、`GAUGE-02`↔2#。
    由此可以**排除「按产线分段编号」的解释**——编码前缀是工艺类型（`SMELT`/`HOLD`/`CAST`/`ROLL`/`DRAW`/`GAUGE`），不是产线，所以序号是按工艺类型编的
  - **但序号只在同类设备内唯一**：车间1 四台不同类型设备的序号都是 `01`，靠编码前缀区分；全局唯一性由 `equipment_code` 的 UNIQUE 约束保证。**名称里的数字不能单独作为设备标识**（四台都叫 1#）
  - **名称本身仍无任何系统约束**：`equipment_name` 既无唯一约束也无格式校验，代码不解析 `#`。所以「1#」这个写法靠的是编码与命名的一致性习惯，改个名字系统不会拦——这一点要单独说明，不能说成"系统强制"
  - **反例（讲解用）**：`DRAW-01 1#拉丝机` 挂在 WS-WIRE 车间2，编号是 1 而在 2 号车间；`GAUGE-02 2#测径仪` 同在车间2。说明序号只在**同类设备内**连续，与车间无关——这正是评审要求「避免直接依据名称推断」的由来
  - 遗留：本次只核实「不依赖名称」，未新增「产线 / 井」维度字段。若业务确需按井、线聚合统计，应另立字段，不能在现有编号上硬套（见第 7 节第 2 条）
