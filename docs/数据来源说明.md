## 1. 四级来源定义

本文用四个级别描述每张表的数据，避免用「真的/假的」这种容易含混的说法：

| 级别 | 含义 | 可信度 | 可否直接清空 |
|---|---|---|---|
| **A｜一期源码定义** | 从一期仓库 `db/migration-mysql/V1__mysql_schema.sql` 与 V2 元数据抄录，编码、名称、归属照原样 | 编号真实存在，但**未与现场核验** | ❌ 不能清，清了系统没有主数据 |
| **B｜联调造数** | 由 `scripts/seed_demo_readings.py` 等脚本按公式生成 | 数值无业务依据 | ✅ 可按标记清除 |
| **C｜人工录入** | 通过系统界面/接口真实创建，内容为编造 | 路径真实、留痕真实、内容不真实 | ✅ 可逐条删除 |
| **空白** | 该字段本应有值但未提供 | 系统如实显示「待补」，不填默认值 | — |

**关键点：A 类不等于「真实数据」。** 我们从未连接过一期的生产库，也没有到车间核对过探头数量。一期上线后可能新增了设备、改了名称、停了产线，这些我们都不掌握。

## 3. 模拟数据与真实数据的对应关系

这是评审最关心的部分：**换掉数据源时，字段怎么对、代码要不要改。**

### 3.1 原始读数 `ods_sensor_data`（B 类，需整体替换）

| 字段 | 当前（模拟） | 接入真实采集后 | 是否需改代码 |
|---|---|---|---|
| `sensor_code` | `TEMP-001` 等 10 个一期编码 | **保持不变**，采集器按同一编码上报 | ❌ |
| `parameter_code` | `temperature` / `pressure` / `level` / `speed` / `diameter` / `tension` | **保持不变** | ❌ |
| `collect_time` | 每 3 分钟一条，从 22:24 到 23:21 严格等间隔 | 采集器实际上报时间（会有缺条、抖动） | ❌ |
| `value_num` | `1090 + 12×sin(i/3) + rand(-2,2)` | 传感器实测值 | ❌ |
| `source_unit` | `℃` / `Pa` / `%` 等 | 采集器上报单位，需与 `dim_unit` 对齐 | ❌ |
| `quality_code` | 硬编码 `GOOD` | 采集器质量码（GOOD/BAD/UNCERTAIN） | ❌ |
| `source_system` | `DEMO-SEED` | 改为采集系统标识，如 `PHASE1_COLLECTOR` | ❌ |
| `source_record_id` | 脚本生成的序号 | 采集器消息 ID，用于幂等去重 | ❌ |

**结论：读数层不需要改代码。** 采集通道接上后，只要按 `sensor_code + parameter_code + collect_time` 写入，页面、历史查询、最新值快照全部自动跟上。

这也解释了测点列表里 `TEMP-001` 显示「数据过期」的原因：数据停在 11-04 23:21，而演示脚本只灌了一批就停了。**这是造数停了，不是设备断采。**

### 3.2 测点与参数（A 类，需现场核验）

| 内容 | 现状 | 真实数据来源 | 处理方式 |
|---|---|---|---|
| 测点编码（`TEMP-001` 等） | 沿用一期 | 一期系统 / 现场铭牌 | 核对一致性，不一致以现场为准 |
| 测点名称、归属设备 | 沿用一期 | 同上 | 同上 |
| 参数编码、单位、小数位 | 沿用一期 | 一期参数表 | 同上 |
| **正常上下限 / 报警上下限** | **NULL（故意留空）** | 工艺卡 / 设备手册 | 现场配置，配置后生成规则版本 v1 |
| **采样周期** | **NULL（故意留空）** | 采集器配置 | 现场配置 |
| **工序绑定** | **NULL（故意留空）** | 车间工艺路线 | 需先补 `dim_process` |

种子文件头原话：*Industrial limits, sampling, and process bindings intentionally remain NULL until configured/verified*。**能确认的照抄，不能确认的留空。**

## 4. 如何识别与清理演示数据

### 4.1 可按标记定位的

```sql
-- 测点（10 条）
SELECT sensor_code, data_source FROM dim_sensor WHERE data_source = 'DEV_DEMO_METADATA';

-- 读数（20 条）
SELECT sensor_code, collect_time, value_num FROM ods_sensor_data WHERE source_system = 'DEMO-SEED';
```

### 4.2 只能按编码/时间识别的

| 对象 | 识别方式 |
|---|---|
| `EQUIP-DEMO-002` | 编码前缀 `EQUIP-`，创建时间 2026-11-03 23:34 |
| 8 台一期设备 | 编码属于一期种子名单，**不可删** |
| 供应商/合同 | 全库仅 1 条，按 ID 定位 |
| 变更记录 | 按 `recorded_at` 时间段筛选 |

### 4.3 清理注意

- `ods_sensor_data` 被写入过的测点，其编码按 S1-P05 规则**被冻结**，不能再物理删除该测点。`seed_demo_readings.py` 当初特意选了要长期保留的 `TEMP-001` 灌数。
- 设备删除走安全删除：先查 10 张关联表，任何一类计数 > 0 即拦截 409。**9 台设备里可删的只有 4 台：`HOLD-FUR-01`、`DRAW-01`、`DRAW-02`、`EQUIP-DEMO-002`**；其余 5 台至少挂着测点（`ROLL-01`、`DRAW-03`、`GAUGE-02` 各 1 类，`SMELT-FUR-01`、`CAST-01` 各 4 类）。

## 5. 接入真实数据的操作顺序

不需要改代码，按这个顺序做：

1. **拿到一期只读连接**，核对 `dim_workshop` / `dim_equipment` / `dim_sensor` / `dim_sensor_parameter` 的编码是否与开发库一致；不一致以现场为准，差异列清单。
2. **补齐设备档案空白**：管理状态、责任人、型号、厂家、购置/投用/质保日期。这一步做完，期限看板才真正可用。
3. **补 `dim_process` 工序表**，否则编辑设备时「所属工序」下拉是空的。
4. **配置阈值与采样周期**，生成规则版本 v1，异常事件才会开始产生。
5. **接通采集通道**，按 `3.1` 的字段映射写入 `ods_sensor_data`，`source_system` 换成真实标识。
6. **替换供应商/合同/附件**为真实台账。
7. **保留全部变更记录**，不清理。

| # | 问题 | 影响 |
