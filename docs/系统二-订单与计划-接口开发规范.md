# 系统二 · 订单与计划接口开发规范

本文供二期前后端开发及联调使用。业务依据见[需求基线](需求基线.md)，43 个接口的编号、方法、路径、入参与校验约束见[订单、库存、排产与交付接口清单](api/订单库存排产接口清单.md)。公共格式沿用[接口通用约定](api/接口通用约定.md)。文中标注「开发约定」的内容补充原清单留给实现的字段细节。所有 ID、日期和数量均为联调示例。

## 1. 页面动作与请求顺序

| 用户操作 | 页面请求及处理 |
| --- | --- |
| 打开「订单与计划」 | 默认进入订单列表，调用 S2-O01。筛选及翻页走服务端。库存、产能和日计划在此模块内部进入。 |
| 新建订单 | S2-I01 读取可选铜丝规格。点击「保存订单」调用 S2-O02，保存成功后可从详情或列表查到订单。 |
| 单单评估 | 从订单详情点击「评估排产」。S2-O03 提供当前版本，S2-P01 提交一张订单。 |
| 联合评估 | 列表批量勾选后点击「联合评估」。同一筛选条件下可跨页保留所选订单。S2-P01 提交所有所选订单及各自版本。查询结果或订单版本变化时保留明确所选项并提示核对。 |
| 进入草稿 | S2-P01 的 `ARRANGEABLE` 带入建议，`NEEDS_ADJUSTMENT` 带入已有结果、缺项和人工编辑依据。两种结果均为 HTTP 200，共用同一草稿。若同规格成品足量，草稿仅有成品分配。 |
| 草稿内调整或修改已生效计划 | S2-P02 读取最新事实和受保护/可替换任务。需要检查既有方案时用 S2-P05。缺项可在原草稿重核用杆量，实际铜板到货与产能变更使用各自命令后刷新上下文。 |
| 确认草稿 | S2-P06 一次生效。成功后可读取 S2-P03/P05、S2-I13/I14 和 S2-D01。冲突时保留编辑及选中项，在草稿内重新读取并核对受影响范围。 |
| 订单变更 | 在详情中分别执行基本信息/改期、优先级、增减量、取消或金额确认。S2-O06 可选，用于先查看影响。预览无业务写入。 |
| 查看可交付条件及交付历史 | 在订单详情调用 S2-D04/D05。用户登记实际交付时调用 S2-D06。交付事实误录走 S2-D07。 |

发布完整流程时，新增或选定需求由 S2-P01 评估一次。按 P1/P2/P3 依赖顺序联调时，P2 可用 S2-P02 直连人工草稿验证同一保存命令，待 P3 接入自动评估入口。关闭未保存草稿丢弃当前临时编辑，原已生效计划和预留继续可查。草稿标识 `clientDraftId` 与 `planId` 独立。

## 3. 请求、状态与并发约定

- HTTP 200 使用 `code=OK`，响应统一带 `code`、`message`、`data` 和 `timestamp`。业务日期为 `YYYY-MM-DD`，时间按 Asia/Shanghai 返回带偏移的 ISO 8601。实际发生的 `businessDate` 和服务端记录时间分列。
- ID 为十进制字符串。版本用 JSON 非负整数。数量用吨对应的十进制字符串，最多三位小数。总金额用人民币元对应的十进制字符串，最多两位小数。实际录入超精度报错。计算中间保留精度，只有计划铜板使用一次 `ceilKg(netNewRodTon × 1.05)`。
- `null` 表示尚无依据或当前不适用，已知零用规范化值。`amountConfirmed=true` 必须存在有效金额，可为明确的 `"0.00"`。调量和不足量结束的约定金额由用户确认。
- `productionResult`、`deliveryResult`、`accountingState` 分列。生产结果引用生产事实和结束操作，直接由成品满足时显示无需生产。可交付依据本订单有效归属和实物，不足量结束保留要求量、实际量和差额。核算状态表达已知及缺项，取消订单没有利润结果。
- 所有业务命令用手填 `operatorName` 和 UUID `requestId`，重要更正按对应接口填写 `reason`。评估和预览是只读 POST。幂等按操作、目标和请求内容核对，同一成功命令的原样重试先回放结果，再考虑当前业务版本。复用成功的 `requestId` 提交不同内容返回 `IDEMPOTENCY_CONFLICT`。编辑字段或刷新版本后重新提交用新 ID。
- `expectedVersion` 是被修改对象的当前版本，`expectedStockVersion` 是同一物料库存的当前版本。**开发约定**。任何影响库存可用量的生效写入，包括仅增加、核销或释放预留，也更新该物料库存版本。查询现货和预期供料分别返回。
- 分页集合返回 `items`、`page`、`pageSize` 和 `total`。默认每页 20 条，最大 100 条，从第 1 页开始。订单默认按交期、创建时间、ID 升序稳定返回，人工优先级另列。日计划读取按日期和车间明确有效范围。
- 多对象确认使用服务器给出的 `expectedVersions`。服务端补全受影响对象范围并核对其中的订单、原方案、任务、物料、普通和日历产能，确认时重新核对保护任务的实际事实。对有投入、领用、称重或已开始的任务返回受保护状态。漏传受影响版本时提示冲突，前端在原草稿重新读取依据。
- **开发约定**。`expectedVersions.capacityOverrides` 的项为 `{workshopId,date,version}`，`null` 表示确无该车间日期的覆盖记录。已撤销的覆盖按当前记录版本核对，页面仍按普通产能显示。S2-C04 恢复已撤销的覆盖使用该记录最新版本。S2-C05 按通用 DELETE 约定补全 JSON `confirmed`，对应用户发起的一次撤销确认。

### 3.1 版本的读取和提交

| 版本字段或集合 | 对象与读取来源 |
| --- | --- |
| 单对象的 `expectedVersion` | S2-O04/O05/O07/O08/O09 取 S2-O03 的订单版本，S2-I03 取 S2-I01 的物料版本，S2-I08/I11 分别取 S2-I06/I10 的原期初或到货事实版本。 |
| 产能 `expectedVersion` | S2-C02 取 S2-C01 的普通产能版本。S2-C04/C05 取 S2-C03 返回的对应日期覆盖版本。全新日期通过 S2-C04 明确提交 `null`。 |
| 交付与归属版本 | S2-D02/D06 取当前订单版本，S2-D03 取 S2-D01 对应原归属版本，S2-D07 取 S2-D05 对应原交付事实版本。均从 S2-I04/I05 读取对应物料的 `expectedStockVersion`。 |
| `expectedVersions.orders`、`plans`、`tasks` | 由 S2-P01/P02 收集受影响订单、已生效方案及任务，分别为 `{id,version}`。S2-P05 提供正在查看的已保存方案及任务版本。 |
| `expectedVersions.inventory`、`capacity`、`capacityOverrides` | 由 S2-P01/P02 收集相关物料余额、车间普通产能、受影响车间日期的覆盖依据，形状依次为 `{materialId,version}`、`{workshopId,version}`、`{workshopId,date,version}`。 |
| `productionScopeVersion` | S2-O03、S2-P01/P02 返回的订单加工范围版本。提交人工用杆总需求时随范围快照传回。在方案确认中放入对应的 `draft.rodDemands[]`。 |

草稿中尚未落库的任务、方案没有正式版本。确认时按关联现场检查已发生实际、有效预留及预期供料。服务端在持锁事务里复核已承诺、已兑现和已释放份额，以及日期先后和当日总量。版本快照用于检测变更，数量和处理结果由当时的有效事实决定。

### 3.2 订单状态与页面文案

下表为三条状态轴的**开发约定**。V4 已使用 `PENDING` 作为初始值，其他英文值由订单、计划、生产与核算共用。订单列表、详情和交付查询使用同一映射。

| 字段 | 枚举与判定 |
| --- | --- |
| `productionResult` | `PENDING` 待安排，`PLANNED` 已安排未开始，`IN_PROGRESS` 生产中，`COMPLETED` 正常生产结束，`SHORTFALL_COMPLETED` 不足量结束，`NOT_REQUIRED` 无需生产，`CANCELLED` 已取消。已有同规格成品全部满足且完成归属确认时为 `NOT_REQUIRED`。任务结束及产量待统计由生产接口提供事实。 |
| `deliveryResult` | `PENDING` 待交付，`READY` 本单已归属真实成品可覆盖尚需交付量，`PARTIAL` 已交付部分，`DELIVERED` 累计足额交付。允许按 S2-D04 的 `canDeliver` 和剩余可交量交付部分有效归属。实际交完不足量的货仍显示已交付量与差额。 |
| `accountingState` | `PENDING` 核算中，适用利润所需事实、金额或成本尚缺。`COMPLETE` 依据齐全，可展示估算盈亏。`NOT_APPLICABLE` 用于取消订单的利润展示，已有实际和成本继续可查。 |
| 已保存方案 `status` | 沿用 V4 的 `ACTIVE`、`SUPERSEDED`、`CANCELLED`。未保存草稿没有方案状态。计划执行结果从生产事实读取。 |

| HTTP 与 `code` | 前端处理 |
| --- | --- |
| 200 `OK` 且评估 `NEEDS_ADJUSTMENT` | 打开草稿并展示已算出的可安排部分、缺项和影响，无需重新发起一次业务评估。 |
| 400 `VALIDATION_ERROR` 或 `PRECISION_EXCEEDED` | 使用 `data.fields` 或兼容 `data.fieldErrors` 定位输入，保留当前表单。 |
| 404 `NOT_FOUND` | 提示所引用对象不可用，刷新来源列表或订单详情。 |
| 409 `VERSION_CONFLICT`、`INSUFFICIENT_STOCK`、`CAPACITY_CONFLICT`、`SUPPLY_CONFLICT`、`STATE_CONFLICT` | 展示 `data.conflicts` 中的对象、版本、日期、差额及受影响任务。更新事实后由用户修改当前草稿。 |
| 409 `DUPLICATE_CODE` | 在订单编号或规格字段提示已存在。 |
| 409 `IDEMPOTENCY_CONFLICT` | 核对是否误用了原请求标识，同一次不确定提交先按原内容查结果。新变更使用新标识。 |
| 422 `MISSING_REQUIRED_DATA` | 按 `data.missingItems` 指出需补依据，例如需要新生产但缺当前加工范围的计划用杆量。 |
| 503 `DATABASE_UNAVAILABLE` 或连接中断 | 保留表单。原样重试业务写入时沿用原 `requestId`。 |

### 4.3 可行性评估 S2-P01

`POST /api/v1/planning/evaluations`

**开发约定**。页面默认评估区间为当天至所选订单的最晚交期，可在草稿发起前修改。最晚交期已在过去时默认至当天，保留原交期并显示延期风险。区间始末随请求传入。

```json
{
  "orderIds": ["9001"],
  "planningFrom": "2027-01-04",
  "planningTo": "2027-01-10",
  "expectedVersions": {
    "orders": [{"id": "9001", "version": 0}],
    "productionScopes": [{"orderId": "9001", "version": 0}]
  }
}
```

  "message": "成功",

    "result": "NEEDS_ADJUSTMENT",
    "affectedOrderIds": ["9001"],
    "productionScopeVersion": 0,
    "productionScope": {
      "orderVersion": 0,
      "wireMaterialId": "103",
      "requiredWireTon": "10.000",
      "actualQualifiedWireTon": "0.000",
      "remainingWireTon": "8.000",
      "finishedAllocationReferences": ["draft:9001:103"]

## 5. 跨模块写入归属及联调检查

| 事实或结果 | 写入入口与读取方式 |
| --- | --- |
| 客户订单、变更和人工金额 | S2-O 系列负责。订单变更保留已有事实，不静默新增或覆盖已生效任务。 |
| 拟分配、计划及预留 | 拟分配随 S2-P06 一次确认。既有订单后来单独分配才用 S2-D02。两个入口复用内部成品分配及库存能力。 |
| 实际投入、称重、领用、停止及实际结束 | 见[生产记录接口](api/生产能源成本接口清单.md)。执行与计划引用同一个任务 ID。产量来自实际称重，成品归属和预留单列。 |
| 实际交付 | S2-D06/D07 统管交付、对应流水、份额核销及成本引用，单事务提交。 |
| 库存与成本 | 各业务写入通过统一库存和成本服务生成、查询和追溯。订单详情读取核算结果与缺项，核算过程由「生产与能源统计」负责。 |

联调至少核对三条链路。全成品可满足时，确认只生效分配和预留，日计划没有新任务。部分成品匹配时，核对剩余加工范围、一次扣除现货和未来供料、一次计算铜板量。两个用户竞争同一份现货时，第一笔成功，第二笔冲突并保留草稿，原成功命令超时重试仍只产生一次事实。交付后检查本单归属、预留核销量、实物差量及库存流水能相互追溯。
