# 系统二 · 生产记录接口开发规范

业务规则依据[需求基线](需求基线.md)第 5.4、8、9.4、11.7–11.12 节。S2-R01 至 S2-R19 共 19 项接口的编号和路径沿用[生产、能源与成本接口清单](api/生产能源成本接口清单.md)第 2 节。通用格式及错误处理见[接口通用约定](api/接口通用约定.md)。本文给出开发阶段的字段命名和报文约定。

## 1. 页面请求顺序

| 页面或动作 | 请求及处理 |
| --- | --- |
| 生产记录首页 | 用 S2-R01 查询当天两个车间的计划任务，依车间及同日顺序展示。日期以 Asia/Shanghai 的业务日为准。打开历史任务时可筛选计划日、实际日、车间和订单。 |
| 任务详情 | S2-R02 读取任务摘要、各实际合计、待补事项和可用操作。S2-R03 按任务加载实际时间线。原始事实或更正依据通过 S2-R04 查看。 |
| 车间一登记 | S2-R07 保存真实铜板投料，允许材料总金额待补。S2-R09 记录每次新增 Φ8 铜杆称重并引用投料及同次归集依据。 |
| 车间二登记 | S2-R10 保存实际交出和当时已知的接收事实，接收未齐留在同一交接的待接收状态。S2-R11 后续补接收。换单或日末称重走 S2-R12，按实际订单和规格填写归属。 |
| 登记停止与结束 | S2-R05 可单独登记实际开始或停止。S2-R15 登记当日任务结束和待称重项。S2-R16 表达整单生产正常结束或不足量结束。S2-R14 单独确认实际无合格产出。 |
| 实际记录历史 | S2-R03 按真实业务日及来源查看计划关联和计划外事实。S2-R04 载入原事实版本，再使用对应更正命令。 |
| 计划外生产 | 首页独立入口。已有实际且找不到已确认任务时用 S2-R17，逐项补录。若找到原任务，从其详情登记或更正，即使实际日期晚于计划日期。 |
| 当日录全确认 | 核对当天已发生的任务内、计划外实际后，用 S2-R18 查看日状态和待补项，再用 S2-R19 确认。金额或能源资料可继续待补，生产记录确认作为完整产量分母的依据。 |

登记第一项投料、交接或称重时，可随该事实提交已经发生的执行片段，服务端一并保存。先进入页面或只登记实际时间不会生成库存变动。

## 3. 查询、数据和一致性

### 3.1 事实字段及状态

- S2-R01 支持 `workshopId`、`orderId`、`plannedFrom`、`plannedTo`、`actualFrom`、`actualTo`、`executionState`、`page`、`pageSize`。首页按计划日取当天两个车间。任务行含 `taskId`、`workshopId`、`materialId`、`plannedDate`、`sequenceNo`、`orderIds`、任务 `version`、各实际业务日和实际状态。`varianceTon` 按已知实际减计划量表达，保留正负号。未称重时实际量与差额均为 `null`。
- S2-R02 在任务行基础上提供订单关联及版本、投入或领用摘要、执行片段、计划预留、适用的库存版本、已知缺项和操作提示。增量登记和更正使用服务端当前版本。页面不累计当前分页来代表日合计。
- S2-R03 支持 `recordType`、`taskId`、`productionGroupId`、`workshopId`、`orderId`、`actualFrom`、`actualTo`、`source`、`page`、`pageSize`。按实际日、录入时间、类型与 ID 稳定降序排列。同一事实关联多个任务或订单仍只返回一条主记录。S2-R04 返回 `original`、`current`、更正链接、库存和成本依据、`missingItems` 与当前版本。
- `recordType` 使用 `EXECUTION`、`PLATE_INPUT`、`ROD_HANDOVER`、`ROD_OUTPUT`、`WIRE_OUTPUT`、`NO_OUTPUT` 白名单。两种称重类型在 V5 由合格产出记录及实际物料区分。`source` 为 `PLANNED` 或 `UNPLANNED`。计划外记录的 `taskId` 为 `null`，返回 `productionGroupId` 和当前 `groupVersion`。供分组显示的 `anchorActualDate` 与各事实 `actualDate` 分开。
- 响应沿用二期现有信封，成功为 HTTP 200 及 `code=OK`。分页返回 `items`、`page`、`pageSize`、`total`，页码从 1 开始，默认 20 条，最多 100 条。业务日期为 `YYYY-MM-DD`，实际和录入时刻为带偏移的 ISO 8601。按业务时区核对时间先后和真实业务日，事后录入保留原实际日。尚未发生的实际不能登记。
- 业务 ID 为十进制字符串。数量吨数用最多三位小数的十进制字符串，人民币总金额最多两位。实际重量超精度报字段错误。执行片段无产量，称重新增量必须大于零。`null` 表示资料未齐，明确零产出通过 S2-R14。交接误差率为比例字符串，`"0.050000"` 表示 5%。服务端按原值判断 5% 边界，再格式化比例。

| 数据轴 | 约定的值及页面判定 |
| --- | --- |
| 任务 `executionState` | `NOT_STARTED` 未开始、`IN_PROGRESS` 进行中、`STOPPED` 已停止、`COMPLETED` 当日任务已登记结束。`waitingForSupply` 和称重状态另列。 |
| `weighingState` | `PENDING` 待称重或待统计，`RECORDED` 已有合格称重事实，`CONFIRMED_ZERO` 明确零产出。已有称重时仍可通过 `missingItems` 表示尚缺同日其他实际。 |
| `handoverState` | `PENDING_RECEIPT` 待接收，`CONFIRMED` 已接收且误差在范围内，`RELEASED` 超差后人工放行。 |
| 订单三类状态 | `productionResult`、`deliveryResult`、`accountingState` 沿用[订单与计划接口开发规范](系统二-订单与计划-接口开发规范.md)。S2-R16 更新生产结果，并返回交付及核算摘要。 |

### 3.2 写入版本、幂等与事务

| 字段 | 来源及校验 |
| --- | --- |
| 通用 `requestId`、`operatorName` | 每次业务写入携 UUID、手填实际经办人。重要更正、计划外补录、不足量结束或明确无产出填写实际原因。 |
| 计划内任务 `expectedVersion` | S2-R05/R07/R09/R10/R15 取 S2-R02 当前任务版本。S2-R14 取请求中指定的任务版本，整车间日确认无任务版本。 |
| 多任务与订单 `expectedVersions` | S2-R12 的 `tasks[{id,version}]` 覆盖所有计划任务，涉及订单归属时 `orders[{id,version}]` 覆盖相关订单。其他命令只在涉及其他订单或相关库存时传回查询提供的对应快照。库存视图约定为 `inventory[{materialId,version}]`。 |
| 更正 `expectedVersion` | S2-R06/R08/R11/R13 从 S2-R04 取原事实当前版本。若改动影响其他订单或库存，同时核对适用的快照及关联事实。 |
| 订单结束 `expectedVersion` | S2-R16 采用订单详情或任务详情读到的订单版本。 |
| 计划外组 `expectedVersion` | S2-R17 首次登记省略版本。追加时使用 S2-R03/R04 或上一次保存返回的 `groupVersion`。该值与组内某一事实的 `version` 分开。 |

版本均为 JSON 非负整数。服务端同时核对库存实物、适用预留、供料、任务和归属所需事实。写入实际记录、入出库、预留变动、归属、可确定的成本依据及更正留痕在同一事务。既有事实真实可独立登记时，成本缺项随结果返回，账务状态留待补齐。

相同已成功请求先按 `requestId`、操作、目标及请求内容校验，原样重试回放首次成功结果。不同内容复用同一 ID 返回 `409 IDEMPOTENCY_CONFLICT`。校验与事务失败保留页面输入。网络结果不明确时原样重试沿用同一 ID，更改内容或版本后提交用新 ID。计划外首次补录同样按此规则回放创建的归集组和事实。

| HTTP 结果 | 典型处理 |
| --- | --- |
| `400 VALIDATION_ERROR` 或 `PRECISION_EXCEEDED` | 根据 `data.fields` 或 `data.fieldErrors` 定位日期、重量、规格、归属或动作类型，保留已填事实。 |
| `404 NOT_FOUND` | 引用任务、归集组或事实不可用，从对应查询刷新。 |
| `409 VERSION_CONFLICT`、`STATE_CONFLICT`、`INSUFFICIENT_STOCK`、`SUPPLY_CONFLICT` | 显示 `data.conflicts` 中的受影响工单、订单、库存或交付信息。在原表单核对适用版本及已发生事实。 |
| `422 HANDOVER_REASON_REQUIRED` | 真值超过 5% 时提示补充原因并由经办人放行。保留两个实测重量。 |
| `422 MISSING_REQUIRED_DATA` | 操作缺少必要依据，例如申请正常结束但产出仍待统计。已经发生的实际停止可单独登记。 |

{

  "expectedVersions": {
    "tasks": [{"id": "7202", "version": 6}],
    "orders": [{"id": "9001", "version": 1}]
  },
  "taskIds": ["7202"],
  "materialId": "103",
  "actualDate": "2027-01-08",
  "stoppedAt": "2027-01-08T15:00:00+08:00",
  "qualifiedQuantityTon": "8.200",
  "rodUseReferences": [{"handoverId": "8201", "sentQuantityTon": "10.000"}],

```

      "orderId": "9001",

      "requestedQuantityTon": "8.200",

  },

```

`stoppedAt` 为真实停止，可同事务新建执行片段，或使用 `executionRecordId` 引用已有片段。多任务同规格的一次真实称重可传已知任务产量份额 `taskShares[{taskId,quantityTon}]`。已知份额之和不得超过实测总量，所有任务份额明确时合计须等于实测总量，仍有未知份额时按任务待补并保留实测总量。订单归属在有关任务份额已知时不得超过该份额。每个订单归属均须符合实际规格、任务或归集证据。换单时实际分开称重则分别提交，规格相同也分别登记。

S2-R12 和 S2-R17 的 `WIRE_OUTPUT` 使用同一归属规则。录入负数、新称重为 `"0.000"` 或请求归属总量超过实测总量时返回 400。任务、订单版本变化时返回 409 并保留表单。版本一致且拟归属超过订单可归属余量时，服务端将该订单归属限制在余量内，差额计入同规格公共份额并返回 `adjustments`。上例实际称重 `8.200` 吨只入库一次，本单尚需 `8.000` 吨并形成对应归属与预留，`0.200` 吨为公共份额。页面明确提示调整，实际重量保持 `8.200` 吨。未齐成本随有效实际返回待核算。

`rodUseReferences[{handoverId,sentQuantityTon}]` 指明本次铜丝称重消耗的实际交出铜杆份额。唯一明确且尚未被其他产出引用的来源可由服务端推导，并在响应返回最终引用。存在多笔交接或跨日多次称重时，单靠同一归集组不足以判定各次成本归属，不能把一笔交出成本重复全额计入多笔产出。未明确来源仍允许保存真实重量，按 `ROD_OUTPUT_LINK_MISSING` 返回待核算。后续通过 S2-R13 补正该字段。

服务端锁定所引用交接，校验归集或任务关系、实际车间、订单份额和引用的正数吨数。所有有效产出累计引用同一交接的吨数不得超过实际交出吨数，更正按原、新引用差额核对。交接更正也须校验已被引用份额。已有真实引用及成本修正留痕。引用本身不触发第二次领料或出库。物理存储复用产出 `input_references` 的类型化关联，与车间一投料 `inputIds` 分别表达并兼容既有引用读取。

### 4.3 其他事实写入的关键字段

| 命令 | 字段与返回约定 |
| --- | --- |
| S2-R05 | `actualDate`、`startedAt`、`stoppedAt`、可选 `notes`。起止至少一项有效，结束不得早于开始。返回 `recordId`、`version`、`taskVersion` 和执行状态。 |
| S2-R07 | `actualDate`、`inputQuantityTon`、可空 `materialAmountYuan`、可选 `productionGroupId`。首次可随真实事实提交 `execution`。返回 `inputId`、版本、归集组、一次出库 `movementId`、预留核销和成本缺项。 |
| S2-R09 | `actualDate`、`qualifiedQuantityTon`、`productionGroupId` 和适用的 `inputIds`、实际起止或执行引用。返回 `outputId`、一次入库 `movementId`、任务累计量、计划差额及成本状态。同一投入在多次称重中作为引用保留。 |
| S2-R06/R08/R11/R13 | `expectedVersion`、实际变化字段、`operatorName`、`reason`。省略字段保持既有值，允许置空的字段以 `null` 表达。R13 可补正 `rodUseReferences`。返回原事实 ID、新版本、`changeLogId`、适用的差量流水及受影响事实。只补金额、说明、接收或产出用杆来源的更正没有数量流水。 |
| S2-R14 | `workshopId`、`actualDate`、`scope` 取 `TASK` 或 `WORKSHOP_DAY`、`reason`。`TASK` 必传 `taskId` 与其 `expectedVersion`，`WORKSHOP_DAY` 校验全天已知事实。返回 `recordId`、版本、范围、`qualifiedQuantityTon: "0.000"` 与 `missingItems`。已存在冲突正产量时返回 409。 |
| S2-R15 | `actualDate`、`stoppedAt`、可选 `notes`、必要的未完成原因及任务版本。返回任务版本、停止依据、实际合格量和差额、待补称重项及未用预留处理结果。只停止且未称重时实际合格量仍为 `null`。 |
| S2-R16 | `endingType` 取 `NORMAL` 或 `SHORTFALL`、实际结束日与结束依据、订单版本。不足量结束必须写 `reason`。返回 `productionResult`、`requiredQuantityTon`、`actualQualifiedQuantityTon`、已有成品分配、`shortfallTon`、本单可交量、核算状态及订单版本。已有合格成品继续用于实际交付，金额另由 S2-O09 维护。 |

### 4.4 明确零产出及误录作废

S2-R14 明确无合格产出时遵循指定范围。`TASK` 只确认该任务实际日，`WORKSHOP_DAY` 包含该车间同日计划内与计划外的实际产出。零确认、合格称重和相关更正在同一车间日锁内互斥校验。重复的有效零范围或已有正产量时返回 `409 STATE_CONFLICT`，附 `recordType`、`recordId`、范围和业务日。原样幂等重试仍返回首个成功结果。

误录的有效零产出通过原 S2-R13 路径更正。以 `POST /api/v1/production/outputs/8302/corrections` 为例。

```json
{
  "requestId": "20000000-0000-4000-8000-000000000006",
  "expectedVersion": 0,
  "operatorName": "李工",
  "reason": "核对过磅单后发现无产出确认误录",
  "changes": {"voided": true}
}
```

此操作仅适用有效 `NO_OUTPUT` 记录。成功后返回同一 `recordId`、新 `version`、`voidedAt` 和 `changeLogId`，保留历史，不生成库存流水。有效统计排除已作废的确认。实际正产出使用 S2-R09、S2-R12 或 S2-R17 另行按真实事实补录。

## 5. 计划外事实 S2-R17

`POST /api/v1/production/unplanned-records` 为单一分类型命令。归集组固定车间、实际产品和首项事实实际日。首项事实提交时省略 `productionGroupId` 与 `expectedVersion`，必填 `workshopId`、`materialId`、`anchorActualDate` 以及 `operatorName`、`reason`，首项 `fact.actualDate` 与 `anchorActualDate` 一致。在首项事实全部通过后建组，将组、实际和适用的流水、归属、预留及幂等结果一起提交。失败时无空组或半套事实。

追加已发生事实时传 `productionGroupId` 和组 `expectedVersion`，沿用组车间与产品。每条保留自己的实际日和原因，末次补录可以与归集首日不同。组首日用于追溯，统计取事实自己的实际日期。已知该事实有对应计划任务时，引导沿原任务登记。日期或规格恰好相同不足以认定为同一任务。

| `recordType` | `fact` 内容 |
| --- | --- |
| `EXECUTION` | `actualDate`、真实 `startedAt`、`stoppedAt` 至少一个、可选 `notes`。 |
| `PLATE_INPUT` | 车间一。`actualDate`、`inputQuantityTon`、可空 `materialAmountYuan`、可选执行片段或引用。 |
| `ROD_HANDOVER` | 车间二。`actualDate`、实际交出和已知接收量、各时间、适用超差放行依据。可按实际事实提供 `orderId`，缺失时按未明确归属保留。 |
| `ROD_OUTPUT` | 车间一 Φ8 铜杆。`actualDate`、`qualifiedQuantityTon`、可用的 `inputIds`、实际起止或片段引用。 |
| `WIRE_OUTPUT` | 车间二的组产品规格。`actualDate`、`qualifiedQuantityTon`、实际起止或片段引用、`allocations[{orderId,quantityTon}]`，可带 `rodUseReferences[{handoverId,sentQuantityTon}]`。涉及订单时传其当前版本，无明确归属时 `allocations` 为 `[]`。用杆来源唯一明确时由后端补出并返回，未齐来源保留重量及成本缺项。 |

首次登记已有的车间一投料。`materialId` 是归集组的产出物料 Φ8 铜杆，投料扣固定铜板物料。

## 6. 联调检查

1. 核对交出、接收晚补、接收超差放行和原样重试。十吨交出只扣一次。仅补接收时保留同一流水及原交接 ID。
2. 同一日 A 订单称重三吨、B 同规格称重四吨，按两次事实登记，车间合计七吨。另用一次称重部分分配的场景核对实物、归属预留和余量。
3. 计划外首项请求校验失败时检查无归集组、无实际事实、无库存变动。成功并重试时组和事实各建一次。继续追加和更正后核对两级版本、实际日、库存与订单关联，计划任务查询仍以已确认任务为源。
4. 只登记停止时显示待统计。明确零产出使用正确的确认范围。已有正产量的范围出现零确认时拒绝并说明冲突。已有八吨、订单要求十吨的不足量结束保留两吨差额，八吨仍可按原订单交付。

## 7. 当日录全状态 S2-R18/R19

当日录全的范围是一车间实际日内已经发生的生产事实，包括计划外事实。S2-R18 返回当日事实修订 `sourceRevision`、日状态 `version`、`confirmedSourceRevision`、经办人和时间、`recordsComplete`、`blockingItems` 及成本类 `missingItems`。它与单任务结束、整单生产结束分别记录。正产量日的完整分母须有有效录全证据，不能只凭已保存记录或日历日期推定。

`GET /api/v1/production/workshops/2/days/2027-01-08/record-status`

```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "workshopId": "2",
    "actualDate": "2027-01-08",
    "version": 8,
    "sourceRevision": 8,
    "confirmedSourceRevision": null,
    "recordsComplete": false,
    "confirmedBy": null,
    "confirmedAt": null,
    "knownQualifiedQuantityTon": "10.000",
    "blockingItems": [],
    "missingItems": [{"code": "ENERGY_PRICE_MISSING", "message": "能源价格待补，成本待核算"}]
  },
  "timestamp": "2027-01-09T09:30:00+08:00"
}
```

尚无日状态行且没有该日事实时返回 `version=0`、`sourceRevision=0`，确认修订与确认元信息为 `null`、`recordsComplete=false`。GET 无写入。存量实际日期迁移或初始化时须有可核对的日源修订，即使尚无确认行也不能将已有事实当作无记录。

```json
{
  "requestId": "20000000-0000-4000-8000-000000000007",
  "expectedVersion": 8,
  "expectedSourceRevision": 8,
  "operatorName": "李工"
}
```

```json
{
  "code": "OK",
  "message": "成功",
  "data": {
    "workshopId": "2",
    "actualDate": "2027-01-08",
    "version": 9,
    "sourceRevision": 8,
    "confirmedSourceRevision": 8,
    "recordsComplete": true,
    "confirmedBy": "李工",
    "confirmedAt": "2027-01-09T09:31:00+08:00",
    "costRunId": "9106",
    "blockingItems": [],
    "missingItems": [{"code": "ENERGY_PRICE_MISSING", "message": "能源价格待补，成本待核算"}]
  },
  "timestamp": "2027-01-09T09:31:00+08:00"

```

R19 在同一车间日锁内核对 `expectedVersion` 和 `expectedSourceRevision`，成功后保存当下源修订、确认人、时间及留痕。新日行首次以版本零及源修订零参与校验，相关唯一键和行锁防并发创建。缺应有的已发生称重、归属或关键实际记录时返回 `422 MISSING_REQUIRED_DATA` 与 `blockingItems`。未发生的计划任务按未执行事实说明，不能因其存在而阻止确认，也不补造开始或结束事实。未来日期返回 400。

材料金额、能源来源、单价待补或尚未发生的接收晚补不单独阻塞已经发生事实的录全声明。已发生的接收等关键实际仍应补录。成本缺项继续影响核算完整性。无合格产出时仍需适用范围的 R14 事实依据，录全确认自身不能补造零产出。

相关实际新增和更正与日状态失效在同一事务。修改实际日时，对原日与新日各推进其 `sourceRevision` 和 `version`，原已确认修订继续供追溯，`recordsComplete` 变为 false。后续核对完成再次用当前版本确认。原确认请求成功后的原样重试返回原结果，重新查询 R18 获得当前是否已失效。确认与补录同时发生时，若事实先提交，旧修订的确认返回 `409 VERSION_CONFLICT` 并提供当前版本和日源修订；若确认先提交，后续合法事实仍可保存，并在同一事务使刚才的确认失效。不会因已有日确认而禁止如实补录。
